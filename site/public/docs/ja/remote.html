リモート magpie

1 つの magpie で複数のコンピューターをまかなえます。プロバイダを保存するコンピューター（デスクトップ、サーバー、Docker で動かす NAS）でサインインとプロバイダ・ルーティンググループの設定を一度だけ行い、ほかの各コンピューターではその magpie を 1 つのプロバイダとして追加します。それがリモート magpie（Remote magpie）です。

共有する magpieほかのコンピューターの magpie
プロバイダ、サブスクリプション、キーここに保存・サインインリモート magpie 経由で使う
ルーティンググループここで作るoffice/group/… として選ぶ
エージェント自分のもの引き続きこのコンピューターの magpie が設定
使用量とクォータここで集計・取得ここに表示（リモートの名前付き）

手元のコンピューターでも magpie は動き続けます。そのコンピューターのエージェントを設定し、モデルを選び、セッションを保存します。モデルだけがもう一方から来ます。

1. メインの magpie を共有する

  1. 共有をオンにするプロバイダを保存しているコンピューターで 設定 → ネットワークと共有 → ローカルネットワークで共有 → オン。magpie はローカルネットワークで待ち受け、Magpie という名前のゲートウェイキーを作ります。スイッチの下の アドレス の行に、ほかのコンピューターから届くアドレス（例：http://192.168.1.20:3425）が表示されます。
  2. コンピューターごとにキーを作るゲートウェイ → ゲートウェイキー、または magpie gateway-key add "Laptop"。sk-magpie-key-… が表示されます。キーごとに日・週・月の上限と使えるモデルを決められ、呼び出しはその名前で集計されます。

共有がオフの間、デスクトップの magpie は自分のコンピューターでしか待ち受けず、ほかのコンピューターからは届きません。Docker の magpie は公開したポートから届き、共有のオン・オフにかかわらず、コンテナの外からの呼び出しすべてにゲートウェイキーを求めます。Docker を参照してください。

2. ほかのコンピューターで追加する

手順 1 のアドレスとキーが必要です。次のどれでも追加できます。

  • アプリ：プロバイダ タブで ＋ プロバイダを追加 を押し、最後の見出し 別のコンピューターの magpie の下にある Remote magpie を選んで、アドレスとキーを入力します。
  • TUI（magpie tui）：Providers ページで a を押し、Remote magpie を選んでアドレスとキーを入力します。その行で w はアドレスの変更、m は一覧の再取得です。
  • CLI：
Shell 
magpie provider add remote-magpie sk-magpie-key-… url=http://192.168.1.20:3425 id=office
magpie models            # office/… が共有する magpie のモデル
magpie provider refresh office   # 一覧を再取得

id= はこのコンピューターでのプロバイダ名で、モデル ID の先頭にもなります（office/…）。アドレスは 192.168.1.20:3425（http:// とみなされます）、末尾に /v1 を付けた形、ルートのどれでも構いません。magpie はどの場合もすべての API をそこにつなぎます。共有元のコンピューターごとに、別の id でリモート magpie を 1 つ追加します。

使えるもの

  • そのモデル。向こうのエージェントに見えるとおりです：office/relay-a/claude-sonnet-5、ラベルは Claude Sonnet 5 · Relay A · office。ID は ID のままで、名前はラベルにだけ付きます。ほかのモデルと同じようにエージェントに選べます。
  • そのルーティンググループ。office/group/… として現れます。振り分けは共有する magpie 上で、そのアカウントを使って決まります。
  • すべての API。リクエストはエージェントが使った API のまま転送されます（Anthropic Messages とトークン計数、Responses、Chat Completions）。共有側のプロバイダが別の API でしか提供しないモデルは、変換が 1 回だけ行われ、両方のコンピューターで変換されることはありません。Responses は WebSocket ではなく HTTP（SSE を含む）で送られます。
  • 画像と動画。画像・動画モデルは自動で見つかり、向こうの画像生成・編集・動画 API を通して使えます。
  • System One。決定モデル（Jev、Clef、自分で名前を付けたモデル）は向こうの /v1/systemone につながり、チャットモデルではなく決定モデルとして現れます。新しいものはプロバイダの一覧を更新すると見つかります。office だけを指定すると一覧の最初の決定モデルに問い合わせます。
  • Embeddings、rerank、音声の文字起こしと音声合成は向こうの対応する API に送られます。エージェントの一覧ではリモートでの扱いのままです。一覧にあっても会話に使えるわけではありません。
  • 価格。各モデルは共有する magpie の計算どおり（向こうで手動設定した価格、なければプロバイダの定価）になるので、2 台の集計は一致します。このコンピューターで設定した価格が優先されます。

クォータと使用量

使用量ページ、メニューバー、magpie quota には、共有する magpie のサブスクリプションカードがその名前付きで（Codex · office、id office/codex）、向こうが最後に読んだ内容で表示されます。ベンダーに問い合わせるのはサインインを持つコンピューターだけです。このコンピューターでカードを更新すると、向こうがもう一度読みます（最大で 30 秒に 1 回）。Codex のリセットや WorkBuddy のチェックインは、向こうのコンピューターのアプリ、TUI、CLI で行います。向こうが予算・モデル・アカウントで制限したキーにはカードは一切渡されず、ここにはそのキー自身のカードと上限だけが表示されます。

共有する magpie は、このコンピューターのリクエストを、送ってきたゲートウェイキーの名前と応答したアカウントで記録します。

短期キー

サンドボックスでエージェントを起動するプログラムは、エージェントごとに自動で失効するゲートウェイキーを渡せます。有効期間は 1 分から 30 日で、一部のモデル、一部のアカウント、有効期間全体のトークン数やコスト、または読み取り専用に制限できます。キー本体は応答に一度だけ含まれます。

Shell 
curl -s -X POST http://127.0.0.1:3425/v1/magpie/keys \
  -d '{"name":"sandbox-1","ttl":"1h","models":["office/codex/gpt-5"],"tokens":200000}'
# {"id":"k…","name":"sandbox-1","key":"sk-magpie-…","expires":"…","models":[…],"limit":{…}}
curl -s http://127.0.0.1:3425/v1/magpie/keys              # 発行したキー（伏せ字）
curl -s -X DELETE http://127.0.0.1:3425/v1/magpie/keys/k…  # 早めに失効させる

このコンピューター上のプログラムはキーなしで呼べますが、ブラウザーのページは呼べません。ほかのコンピューター、コンテナー、CI は、キーの発行を許可したゲートウェイキーを付けて呼びます。そのキーが発行したキーはすべてそのキーに縛られます。使えないモデルやアカウントは使えず、そのキーより後まで有効にはならず、使った分はそのキーの上限に数えられます。オフにするか削除すると、発行したキーもすぐに使えなくなります。コマンドラインでも同じで、キーだけを出力します。

Shell 
magpie gateway-key issue --ttl 1h --name sandbox-1 --models office/codex/gpt-5 --tokens 200000
magpie gateway-key issuer <id> on    # このキーにキーの発行を許可
magpie gateway-key issue --ttl 30m --from <id> --read-only --json
magpie gateway-key list               # until 10-31 14:00、expired、issued by …

期限切れのキーは、どの API でも理由付きの 401（“the gateway key "sandbox-1" expired at …: ask for a new one”）で断られます。このコンピューターからでも同じです。1 時間後に削除されます。

GitHub Actions のキー

GitHub Actions のジョブは、リポジトリの secrets にゲートウェイキーを置かなくても短期キーを受け取れます。GitHub が渡す OIDC トークンと交換します。リポジトリ（必要ならブランチ、environment、任意の claim。完全一致か * 付き）、発行に使うゲートウェイキー、有効期間を指定するルールを書きます：

Shell 
magpie gateway-key issuer <id> on
magpie gateway-key oidc add --key <id> --repo owner/app --ref refs/heads/main --ttl 1h
# ルール id と audience（magpie-<ルール id>）を表示
magpie gateway-key oidc list
magpie gateway-key oidc remove <rule id>

ワークフローでは、ルールの audience 付きトークンを GitHub に求め、/v1/magpie/keys/oidc に POST します：

YAML 
permissions:
  id-token: write
steps:
  - name: Get a magpie key
    run: |
      TOKEN=$(curl -s -H "Authorization: Bearer $ACTIONS_ID_TOKEN_REQUEST_TOKEN" \
        "$ACTIONS_ID_TOKEN_REQUEST_URL&audience=magpie-<rule id>" | jq -r .value)
      KEY=$(curl -s -X POST https://<your magpie>/v1/magpie/keys/oidc \
        -H "Authorization: Bearer $TOKEN" -d '{"ttl":"30m"}' | jq -r .key)
      echo "::add-mask::$KEY"
      echo "MAGPIE_KEY=$KEY" >> "$GITHUB_ENV"

キーはルールのゲートウェイキーの下で発行され、他の発行済みキーと同じくそのキーに縛られ、ルールの期間より長くは有効になりません。名前はリポジトリ、ブランチ、実行番号です。別のリポジトリやブランチのトークン、期限切れ、交換済みのトークンには理由付きの 401 が返ります。他のコンピューターから使えるのは magpie を共有している間だけで、断られたトークンは認証失敗の回数に数えられます。ルールがなければ何も交換されません。

管理 API

プロバイダー、アカウント、ゲートウェイキー、アカウントグループは、許可したキーがあれば設定ファイルを手で編集せずに管理できます。許可はコマンドラインで行います（API 経由ではできません。キーは自分以上の権限を別のキーに与えられません）。

Shell 
magpie gateway-key add automation
magpie gateway-key admin <id> local   # このコンピューターのみ
magpie gateway-key admin <id> any     # ほかのコンピューターからも
curl -s http://127.0.0.1:3425/v1/magpie/admin/providers -H "Authorization: Bearer $KEY"
curl -s -X POST http://127.0.0.1:3425/v1/magpie/admin/gateway-keys/add-key \
  -H "Authorization: Bearer $KEY" -d '{"name":"ci"}'

アプリ自身のページと同じ処理が /v1/magpie/admin/ の下にあります。GET providers、POST provider/{save,delete,on,off,name,…}、POST keys/…（プロバイダーのキー）、GET/POST gateway-keys[/{add-key,rename-key,limit-key,models-key,remove-key,…}]、GET/POST account-groups[/…]、そして POST signin（{"agent":…}）は、ベンダーのページと入力するコードを返し、パスワードは受け取りません。ブラウザーのあるコンピューターで開いてください。保存済みのキーとゲートウェイキーの秘密は再び返されず、このコンピューターのほかのアプリを変更する操作も提供しません。

読み取り専用キー、拡張機能のキー、発行されたキーや短期キー、共有キーは使えません。キーの有無にかかわらず Web ページからは呼べません（Origin や Sec-Fetch-* を持つリクエストはすべて拒否）。このコンピューターの別名で届いたリクエストも拒否されます。ネットワーク越しに共有している場合、any のキーだけが通ります。

統計 API

使用量ページの内容は JSON でも、このコンピューターに、また magpie を共有している間はゲートウェイキー付きのリクエストに提供されます。予算、モデル、アカウントで制限されたキーには、自分のリクエストと上限だけが返ります。持ち主がそのキーの残量をオンにすると（magpie gateway-key quotas <id> on）、使えるもののクォータも返ります。

  • /v1/magpie/usage?period=today|7d|30d|all：合計と、モデル、エージェント、プロバイダー、アカウント、ゲートウェイキーごとの内訳。
  • /v1/magpie/usage/requests：リクエストログ。period、day、offset、limit と、絞り込みの model、agent、provider、account、callerKey、failed=1、retried=1、q。
  • /v1/magpie/usage/requests?cursor=start：同じリクエストを変更として読み、自前の台帳を保てます。安定した id で upsert する rows（original_ids 付き）、deleted、next_cursor、has_more。cursor=now はそれ以降だけを読み、再開できないカーソルは code 付きで拒否され、黙って飛ばされることはありません。
  • /v1/magpie/quotas：各サブスクリプションのウィンドウ（?kept=1 でベンダーに問い合わせない）。/v1/magpie/quotas/history?days=：残量の履歴、最大 45 日。
  • /v1/magpie/limit：キー自身の上限、有効期限、発行元キーの上限。制限されたキーには、何で制限されているか（heldTo）、使えるモデル（models）、クォータが返るか（quotas、quotaProviders）も。
  • /v1/magpie/concurrency：アカウントごとの実行中のリクエスト。
Shell 
curl -s 'http://127.0.0.1:3425/v1/magpie/usage?period=7d'
curl -s 'http://127.0.0.1:3425/v1/magpie/usage/requests?period=today&callerKey=k…&failed=1&limit=50'
curl -s 'http://127.0.0.1:3425/v1/magpie/quotas?kept=1'
curl -s 'http://127.0.0.1:3425/v1/magpie/quotas/history?days=14'
curl -s http://127.0.0.1:3425/v1/magpie/limit -H 'Authorization: Bearer sk-magpie-…'
curl -s http://127.0.0.1:3425/v1/magpie/concurrency

うまくいかないとき

表示対処
「magpie isn’t shared on the local network」または「remote magpie isn’t shared」そのコンピューターで ローカルネットワークで共有 をオンにする
「remote magpie didn’t take this key」（401）向こうの有効なゲートウェイキーを使う：向こうの ゲートウェイ → ゲートウェイキー
モデルで 403そのキーは一部のモデルしか使えない可能性があります。向こうで magpie gateway-key models <id> を実行すると確認・変更できます。office だけだとキーの許可に関係なく System One の最初の決定モデルに問い合わせます。完全な office/provider/model ID を使ってください
「couldn’t reach the remote magpie」アドレス、向こうで magpie が共有オンで動いているか、ファイアウォールがポートを通すかを確認する
System One のモデルがない、または「doesn’t share its quotas」向こうの magpie を更新し、こちらで一覧を更新する
外出先からは、Tailscale や WireGuard などの VPN 越しに、VPN 上のアドレスで共有する magpie に届くようにしてください。ポートをインターネットに開けないでください。
