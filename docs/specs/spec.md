# 规范：基于现有用量账本的独立分析看板（Issue #213）

## 1. 目标与数据范围

分析看板用于查看已有调用记录的可靠性、端到端首字延迟、解码速度、成本与缓存表现。用量页继续展示 Token 与消耗，分析页通过模型、供应商、客户端排行定位异常，并支持实体调用明细。

数据来源为现有 `usage.jsonl` 和 `usage.Record`。使用已有的 `model`、`provider`、`agent`、`status`、`ms`、`ttft_ms`、`in`、`out`、`cache_read`、`cache_write`、`reasoning`、`effort`、`host`、`session`、`kind`、`t`。沿用现有落盘与首字计时，不增加账本字段或修改网关写入路径。

分析的是账本中最终调用结果；供应商分组使用 `provider`。取消账号归因、尝试级失败分析、真实尝试首字延迟、前置等待分解以及时间桶／状态切片／延迟和 Token 分桶下钻。

## 2. 需求与验收标准

1. **导航与周期**：新增 `#view-analytics`，从用量页头部进入，继承 `Today`、`7d`、`30d`、`All` 周期；返回时保持用量页滚动位置与标签状态。
2. **已有实体维度**：提供 `[全部]`、`[按模型]`、`[按供应商]`、`[按客户端]`。供应商只按 `provider` 分组。模式切换是前端展示选择，服务端每次返回三个维度的排行。
3. **互斥筛选**：按 X 时清除 X 的筛选，保留另外两个维度；全部模式保留当前筛选。每次筛选变化重新请求服务端，在完整周期记录上过滤后聚合。
4. **六张图与主题磁贴**：可靠性包含错误率排行与只读异常趋势；响应速度包含端到端 TTFT 排行与解码速度排行；成本与缓存包含成本排行与缓存命中率排行。详细口径见 [仪表盘设计](dashboard.md)。
5. **实体下钻**：点击排行实体或全部模式数字卡片，在该图表下方展开最多 50 条明细。异常趋势只展示时间变化。调用详情仅展示账本已有字段，见 [明细设计](detail.md)。
6. **交互约束**：同时只展开一处明细；沿用 `.view` 点击锚点与 ResizeObserver 持续补偿，禁止自动跳滚；所有文案中英双语。

| 编号 | 验收标准 | 验证方式 |
| :--- | :--- | :--- |
| AC-1 | 使用现有账本字段，模型、供应商、客户端分组可用于历史记录 | 合成记录与既有账本读取验证 |
| AC-2 | 同一响应包含整体指标与三个维度的排行；切换展示模式及互斥筛选正确 | 后端结果与 GUI 核验 |
| AC-3 | 每次分析只加载一次周期记录，过滤后计算指标；筛选后分位数与比例正确 | 聚合测试与代表性账本性能测量 |
| AC-4 | 五种排行按各自方向排序，异常趋势只读，实体下钻先筛选排序后截取 50 条 | 后端与浏览器验证 |
| AC-5 | 缓存率沿用现有用量界面；有效首字与解码样本沿用现有条件 | 边界数据验证 |
| AC-6 | 下钻及详情展开不跳动，中英文标签完整 | Chromium 与 WebKit 核验 |

## 3. 指标约定

- 成功率为 `status < 400` 的记录数 / 总记录数。错误率为 429、5xx、其他 4xx（排除 499）之和 / 总记录数；取消数量单独展示。
- 首字延迟直接使用 `ttft_ms`，只取 `status < 400 && ttft_ms > 0` 的有效样本，计算 P50/P95。这里的 TTFT 是网关已有端到端首字计时。
- 解码速度沿用 `Totals.Speed()`：仅取 `status < 400 && ttft_ms > 0 && out > 0 && ms > ttft_ms` 的记录，以总输出 / 总解码时间计算，禁止对逐调用速度作简单平均。
- 缓存率严格沿用 `app.js` 用量页公式：`sum(cache_read) / (sum(in) + sum(cache_read))`；分母为 0 时显示 `—`。`cache_write` 单独展示写入量，不加入此命中率分母。该分母称为“缓存率统计输入量”；完整提示词总量另按 `in + cache_read + cache_write` 展示。
- 成本复用用量页的 models.dev 列表价与未定价处理。
- 排序门槛：错误率使用总调用数 ≥ 10；TTFT 使用有效首字样本数 ≥ 10；解码速度使用有效解码样本数 ≥ 10；缓存率使用缓存率统计输入量 ≥ 10k。全部模式不作排行门槛过滤，指标没有有效样本时显示 `—`。

## 4. 服务端聚合与查询契约

### 4.1 分析响应

`GET /api/analytics` 使用 `period`、`model`、`provider`、`agent` 参数。筛选值为空表示全部；周期定义沿用现有用量页。

服务端读取一次周期记录，在当前筛选条件下同时累计整体、模型、供应商、客户端与异常趋势。响应固定包含：

- `period`、`bucket`：当前周期与趋势桶粒度，沿用用量页 Today 小时、7d/30d 天、All 周。
- `summary`：整体调用数、成功率、错误率、429/5xx/其他 4xx 数、取消数、TTFT P50/P95、有效首字样本数、解码速度与有效解码样本数、成本与未定价数、输入／输出／缓存读取／缓存写入量、缓存率。
- `rankings`：固定包含 `model`、`provider`、`agent` 三套排行；每套包含 `by_error_rate`、`by_ttft`、`by_speed`、`by_cost`、`by_cache_rate`。
- `error_trend`：当前筛选下的只读错误趋势，按 429、5xx、其他 4xx（排除 499）分段展示。
- `filters`：当前周期已有 `model`、`provider`、`agent` 值，供筛选器使用。

每个排行条目携带原始实体键、样本数、该指标值及结构化辅助数据：状态次数、TTFT P50/P95、Token 量、成本与占比、样本不足／无缓存记录／未定价标记。辅助文案由前端 i18n 生成。`Analyze(p Period, filter Filter) AnalyticsData` 的 `Filter` 仅包含 Model、Provider、Agent。

### 4.2 实体明细

`GET /api/analytics/calls` 继承 `period`、`model`、`provider`、`agent`，附加 `chart_id` 和 `limit`（默认且最多 50）。前端将点击实体写入其对应的已有筛选参数：按模型写 `model`，按供应商写 `provider`，按客户端写 `agent`；全部卡片直接使用当前筛选。

`chart_id` 为 `1.1`、`2.1`、`2.2`、`3.1`、`3.2`；只读图表 `1.2` 不提供下钻。`RecentCalls(p Period, filter Filter, chartID string, limit int) []Record` 在完整周期记录上先应用筛选和图表口径、排序，再截取最多 50 条。排序与过滤见 [仪表盘设计第 8 节](dashboard.md)。

## 5. 前端交互

- 全部模式显示 `summary`，分组模式显示 `rankings` 中选定的一组；模式本身不作为请求参数。模式切换如清除了现有筛选，重新请求分析结果；筛选条件未变时直接切换展示。
- 用户修改筛选或周期时，调用 `/api/analytics` 重新聚合；前端只格式化及绘制服务端结果，不从已汇总排行重新计算交叉指标或 P95。
- 筛选或模式变化时收起旧明细，避免展示条件不匹配的调用列表。
- 条形和全部数字卡片支持原地下钻，异常趋势仅展示。交互详见 [交互设计](interaction.md)。
- 明细包含现有 `session` 等可能带邮箱的文本时，复用全局 Hide emails；注册 `pages` 时提供视图及掩码按钮选择器，并在布局中提供对应按钮。

## 7. 决策结论

只分析现有账本字段；保留整体、模型、供应商、客户端展示；六张图按可靠性、响应速度、成本与缓存分组。缓存率沿用现有界面；筛选由服务端计算；错误率、TTFT、成本降序，速度与缓存率升序。账号与尝试计时扩充、时间桶和状态切片下钻已取消。
