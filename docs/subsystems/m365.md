# Claude for Microsoft 365 HTTPS gateway

Claude's Word, Excel and PowerPoint add-ins run in a browser control. Their
configured gateway therefore has to be trusted HTTPS and has to answer the
browser's CORS and Private Network Access preflight. Magpie keeps its ordinary
HTTP gateway for agents and, when the user turns Microsoft 365 support on,
serves the same routing handler on a second loopback-only HTTPS listener.

## Responsibilities and sources of truth

| Part | Responsibility | Source |
| --- | --- | --- |
| Setting | `Settings.M365` enables the listener. `M365KeyID` points to the normal named gateway key used by the add-in; the credential remains in `caller-keys.json`. | [`settings.go`](../../internal/settings/settings.go) |
| HTTPS listener | Binds `127.0.0.1:8787`, TLS 1.2 or newer, and exposes only `GET /v1/models`, `POST /v1/messages` and their preflight. It passes requests to the same `Server.Handler` as the HTTP gateway, so routing, usage, limits and streaming are not duplicated. | [`m365.go`](../../internal/gateway/m365.go) |
| Certificate | Generates a local CA with critical DNS/IP NameConstraints for only `localhost`, `127.0.0.1` and `::1`, then a leaf for those names. The leaf private key is mode 0600; the CA private key is never written. | [`m365_cert.go`](../../internal/gateway/m365_cert.go) |
| Browser boundary | Enabling adds `https://pivot.claude.ai` to the existing origin allowlist; disabling removes it. The existing CORS guard answers PNA and requires an enabled named gateway key from every allowed page. | [`cors.go`](../../internal/gateway/cors.go), [`m365.go`](../../internal/gui/m365.go) |
| UI and lifecycle | Settings shows the endpoint, certificate state and key. The desktop process starts and stops the HTTPS listener with the gateway it owns; another Magpie process serving the gateway cannot be configured from this one. | [`backend.go`](../../internal/gui/backend.go), [`app.js`](../../internal/gui/assets/app.js) |

## Runtime path

1. The user turns Claude for Microsoft 365 on in Settings.
2. Magpie creates or reuses the named `Claude for Microsoft 365` gateway key,
   adds the add-in origin, saves the setting and restarts its gateway.
3. The gateway creates the certificate files if needed and listens only on
   `https://127.0.0.1:8787`. Certificate creation does not trust it.
4. On macOS the user explicitly chooses **Trust certificate**, which adds it
   to the user's default keychain. Other systems show the certificate path for
   manual trust. The automatic Windows action remains unavailable through the
   UI and API until its full install, Office use and removal path has been
   exercised on Windows.
5. The add-in sends its key by `x-api-key` or Bearer auth. `lanGuard`,
   `corsGuard`, caller limits and the regular Anthropic route all run as for
   any named gateway caller.
6. Turning support off first saves the setting as off, removes the add-in
   origin and stops the HTTPS listener. On macOS it then removes Magpie's CA
   from the user's trust store; other systems tell the user to remove a
   manually installed CA. A trust-store error cannot leave the integration
   on: it is reported with manual removal instructions. The named key remains
   so a later enable can reuse it; it may be revoked from Gateway keys at any
   time.

## Constraints and failure behavior

- Port 8787 is fixed because the add-in's Gateway sign-in defaults to
  `https://127.0.0.1:8787`; its URL field can be edited, but Magpie keeps the
  documented default. A process already using it leaves Microsoft 365 support
  stopped and its error is shown in Settings, including after the switch rolls
  back to off.
- The HTTPS listener never binds a LAN address and exposes none of Magpie's
  quota, MCP or administration routes.
- A listed origin without an enabled key is refused, as every browser caller
  is. An unlisted remote web page is refused before it reaches a provider.
- Automatic trust management is exposed on macOS. Windows keeps the command
  implementation and tests, but its UI and API actions remain disabled until a
  real Windows Office run verifies installation, use and removal; it and other
  systems show the certificate path for manual installation.
- Regenerating an invalid, unconstrained or near-expiry certificate first
  removes the old CA if it is trusted, then creates a new CA because the CA
  private key is intentionally not retained; the new CA must be trusted.
