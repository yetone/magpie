# Plugin tools

A community plugin (an OpenCode plugin, an npm package in the plugin host) can give tools: OpenCode's `tool` hook, `{tool: {name: tool({description, args, execute})}}`. In OpenCode only OpenCode's own model can call them. magpie offers them to every agent instead, as an MCP server of its own at `/mcp/magpie/tools` (Streamable HTTP), which any agent that takes an MCP server can be given. It is the gateway's tool point (P4 of [Plugin runtime](plugin-runtime.md)) opened to community plugins. The built-in plugin `tools` serves it. The provider plugins in the same host are [Provider and plugin ownership](provider-plugins.md); the gateway middleware is [Gateway middleware](gateway-middleware.md).

## Responsibilities and sources of truth

| Part | Responsibility | Source |
| --- | --- | --- |
| Collect | Each loaded plugin's tools: the names that match `^[A-Za-z0-9_-]{1,48}$` and have an `execute`, the last of a name winning, as in OpenCode. Each tool's `args` becomes JSON Schema: a zod shape (v3 or v4, `.describe`, `.optional`, `.default`, enums, arrays, nested objects) or a zod object, while a plain JSON Schema object is kept as it is. They are returned with the plugin list (`Loaded.Tools`). | `toolsOf`, `jsonSchema`, `argsSchema`, `toolList` in [`host.js`](../../internal/plugin/host.js); `Tools` in [`tools.go`](../../internal/plugin/tools.go) |
| Run | The host's `tool` call: it checks the arguments against the tool's own zod schema (defaults filled in; a wrong argument is an error naming its path), then races `execute(args, ctx)` against `ToolTimeout` (55s, under the 60s an MCP client gives a call). `ctx` is OpenCode's: `agent` is the calling agent as the gateway knows it, `abort` fires at the timeout, and `directory` is the host's. A string answer is the text, `{output}` its output, and anything else is its JSON. | `parsedArgs`, `runTool` in `host.js`; `RunTool` in `tools.go` |
| Note | After every load the host notes which plugins gave which tools in `plugin-tools.json` (settings dir), written whole and only when it changed. `ToolsOn` counts the plugins that are on in plugins.json and have tools there. A note that can't be read or parsed is an error, so the plugin stays on. `ToolNames` is the note for a Plugins page whose host isn't running. | `noteTools`, `ToolsOn`, `ToolNames` in `tools.go` |
| Serve | `tools/list` names each tool `<plugin>_<tool>`: the plugin's short name, as its Plugins row names it (`plugin.ShortName`, which takes off the scope and one leading `middleware-`, `opencode-`, `tools-`, `page-` or `agent-`: opencode-weather-tools → weather-tools, @magpie-community/tools-calc → calc; a plugin added from a folder, the folder's name), at most 24 characters, in `[A-Za-z0-9_-]`, then the tool. Each name is at most 64 characters, and a name two would share gets `_2`, `_3`. `tools/call` runs one; an unknown name is error -32602. | GUI | Each Installed row of a plugin that is on and gives tools lists them by their MCP names, each with its description on hover, plus a button that copies the server's address (`mcpAddress`). plugins.json is the source of truth for which plugins are on. The host only loads those, so only their tools are listed.

## Runtime path

1. An agent's MCP client posts `tools/list` to `/mcp/magpie/tools`. `servedTools` returns nothing while the point isn't served or no plugin is on; then the plugin host (Bun) isn't started for it. Otherwise it asks the host for its plugins' tools (`plugin.Tools`, which starts the host if need be) and names them (`namedTools`).
2. `tools/call` finds the tool by its MCP name in the same list. While the point is off it answers `isError` "magpie's Plugin tools plugin is off…", without asking the host.
3. `toolsMCPRun` holds the call to the calling gateway key's limit through `reserveFor`, the same way in as the chat APIs and the search MCP server ([Plugin runtime](plugin-runtime.md), budget point). A refusal, or a limited key with the Key limits plugin off, is an `isError` answer, and the tool isn't run.
4. `plugin.RunTool` asks the host to run it. The answer, or the error (`<tool>'s arguments are wrong: …`, `<tool> took longer than 55s`, or what the tool threw), goes back to the agent as the call's text, with `isError` set on an error.

A tool's answer goes back to the agent that called it, on this computer or on a shared one with a key. It never goes to a vendor, so masking has nothing to do with it. Whatever the agent sends a model next is masked as any request is.

## Constraints and failure behavior

- Off means off: no tool is listed, a call says the plugin is off, and the host is not asked (`TestToolsMCPOff`).
- A plugin's tool runs in the plugin host with the user's rights, as its provider code does. Installing a plugin is trusting it.
- One host serves every plugin. A tool that never answers is answered at `ToolTimeout`, and its call's slot in the host is left for its own abort to end; the host goes on serving (`TestPluginTools`).
- Names are stable for a given set of plugins on. Turning on a plugin earlier in plugins.json that gives a tool of the same MCP name renumbers the later one.
- Each plugin that is on and gives tools is also a [Library](library.md) server of its own (chenxiang0010 on Discord: Search1API's tools in the MCP router), so magpie wires it like any other ([`plugin_tools.go`](../../internal/library/plugin_tools.go)):
  - Once the host has noted the plugin's tools (plugin-tools.json, `plugin.ToolsNoted`), the library adds an `http` server named by the plugin's short name (`search1api`, `search1api-plugin` when a server has that name), with `plugin` set to the plugin's name and its URL `/mcp/magpie/tools/<short>` (`ToolsMCPOne`), which serves that plugin's tools alone, each by its own name.
  - Added with the MCP router on, it is on for the agents given the router's entry, so its tools are in their router at once as `<short>__<tool>`; with the router off it is on for none until the user switches it on. Per agent and per tool it is then switched like any server.
  - The router runs its tools in this process (`gateway.PluginToolsOf`, `RunPluginToolOf`), under the same Plugin tools gate. With the router off an agent is given the gateway's address of the plugin's tools as it reaches the gateway (`through`), with a key from another machine.
  - It is `local`: a carry or backup never takes it to a computer that may lack the plugin. It is offered once (`pluginsOffered`): a server the user removed comes back only when the plugin is removed and added again. The plugin removed takes its server out; turned off, the server stays and lists nothing. A plugins.json that can't be read changes nothing.
  - `/mcp/magpie/tools`, every plugin's tools under one server, stays for agents wired to it by hand.

## Search APIs from a plugin

The same host and `Loaded` list carry a second hook, `search`: `{search: {<id>: {name, keysURL?, keyOptional?, url?, auth?, execute({query, count, key, url}, ctx)}}}`, which adds a web search API to magpie's own ([`provider.SearchVendors`](../../internal/provider/search_api.go)). It is not part of the tools MCP server; it belongs to the search path ([Gateway routing](gateway-routing.md), "A search API's base URL").

| Part | Responsibility | Source |
| --- | --- | --- |
| Collect | `searchesOf` keeps the ids that match `^[a-z0-9][a-z0-9-]{0,31}$` and have an `execute`; `searchList` returns `{id, name, keysURL, keyOptional, needURL, auth}` with the plugin (`auth` only when it names a provider this plugin's auth hook signs in to, `searchAuthOf`) (`Loaded.Searches`). | `searchesOf`, `searchList` in [`host.js`](../../internal/plugin/host.js); [`search.go`](../../internal/plugin/search.go) |
| Note | After every load the host notes them in `plugin-searches.json` (whole, only when changed). `NotedSearches` reads it without starting the host (`filememo`), for plugins that are on in plugins.json; a note that can't be parsed is an error, and `AllSearchVendors` then adds none. The API's vendor id is `<plugin short name>:<id>` (`PluginSearch.VendorID`), so it can't take a built-in's id. | `noteSearches`, `NotedSearches` in `search.go` |
| List | `provider.AllSearchVendors` is `SearchVendors` plus the noted ones; `SearchVendorOf`, `Ready`, `check` and the GUI's `searchVendors` use it. A user's saved key and order stay in providers.json under that id; with the plugin off or removed the API is not ready, so never asked, and comes back with the plugin. | `search_api.go` in `internal/provider`, `searchVendorJSON` in [`api.go`](../../internal/gui/api.go) |
| Ask | `askSearchAPI` hands a plugin's vendor to `askPluginSearch`, below `askSearchAPIKeys`: the same keys, rest, timeout (a quarter of `searchTimeout`) and request-log row as a built-in, with the query `apiSearch` already masked. `plugin.RunSearch` runs the host's `search` call; a throw with a numeric `status` comes back as `SearchRefused`, which becomes `searchRefused`. Pages are cleaned with `searchPlain` and `clipText`, six at most. | `askPluginSearch` in [`search_api.go`](../../internal/gateway/search_api.go) |
| Sign in | An entry with `auth` (`SearchVendor.Auth`) is ready with no key. `askSearchAPIKeys` hands it to `askSearchSignedIn`: `provider.SearchSignIn` finds the plugin's provider (`plugin:<auth>` of the same plugin) and its name; none is "not signed in to X: sign in to it on Providers", and the next search API is asked. Its accounts are the ones a model request takes (`accountsOn`: own unless paused, then `AlsoOn`, by `LoginRanks`), in `searchKeyOrder`'s order, each with a quarter of the search's limit, a request-log row named by the account's user and its own search rest (`searchKeyID` of `account <key>`); a refusal rests it for search only (`restSearchKey`), never `restingUntil`, and the next account is asked. `plugin.RunSearchAs` sends the account's key and its proxy; the host's `runSearch` checks the key is this provider's and signed in, renews it under `fresh` (its wait counts within the call's time, `late`; an account signed out mid-renewal stays out and the search fails), runs the hook inside `inScope`, so a token it saves with `client.auth.set` goes to that account, and gives `ctx.getAuth()` a copy of that account alone. The GUI's `searchVendorJSON.auth` says the provider's name, whether it is signed in and how many accounts are on (`gateway.SearchAccountsOn`); `settings.js` shows that in the key's place. | [`search_signin.go`](../../internal/gateway/search_signin.go), [`search_signin.go`](../../internal/provider/search_signin.go), `runSearch` in `host.js`, `RunSearchAs` in `search.go` |

Constraints: the plugin runs with the user's rights and sees the key and the (masked) query, as a built-in's vendor does. A backup or sync that restores search APIs on a computer without the plugin drops the plugin's entry there (`RestoreSearchAPIs` keeps only vendors it knows). The vendor list is read from the last load's note, so a plugin just added is listed after the host has loaded it. Tests: `TestPluginSearch` (host, `testdata/search`), `TestPluginSearchSignsIn` (host, `testdata/searchauth`: the chosen account's sign-in only, renewed when due within the timeout, an unknown or other provider's account refused, unbound entries unchanged), `TestPluginSearchAPI`, `TestPluginSearchAPISeesMaskedQuery` and `TestPluginSearchSignsIn` (gateway: signed out falls through to the next API, accounts off are skipped, a 429 rests the account for search and not for models), and `search-signs-in.test.cjs` (GUI).
