# Agent wiring

magpie connects a coding agent to its gateway by editing the agent's own
config. That covers the endpoint, the key `magpie-<agent>` and the model,
in the agent's own format. When the agent is disconnected, magpie puts back
what the agent had before. Package `internal/agent` describes every
supported agent: where its config lives, which fields matter and which
values to offer. It also records what magpie set, so a later change made by
something else shows up as drift.

## Runtime path

1. **Connect.** The Agents page's switch calls `ConnectHow` (`POST /api/agents/{action}/{id}` in [`internal/gui/api.go`](../../internal/gui/api.go)). It stashes the current values (`<id>.connect.was`). It brings back the models used before a switch-off (`reconnect`), or calls `Join` where the agent keeps its own model (Codex signed in with ChatGPT). `reconnect` calls `Join` first too, so a Codex switched off on a routing group comes back joined, as the switch first connected it: put back on the group alone it was beside its sign-in only, and an own model picked on the Agents page took it off magpie (NancyTom18 on X, `TestCodexReconnectStaysJoined`). One that can't join then (a provider of the user's own, magpie API) is connected as at first unless its own model was one of magpie's: its memories' or subagents' model put back alone read as connected while its own model stayed off magpie (#3868, `TestCodexOffAndOnJoinsAgainWithItsHelpersOnMagpie`). Otherwise it picks a model by the order `ConnectHow` documents and sets it through `Apply`.
2. **Pick.** `Pick` sets a field from the model picker. Picking one of magpie's models on an agent that isn't connected connects it first. Each row of a model picker that a provider served with a timed reply this week says how fast: tokens a second, or the first token's wait when only that was timed (`speedTag` in app.js, from `GET /api/model-speeds`, `modelSpeeds` in [`internal/gui/speeds.go`](../../internal/gui/speeds.go): the usage ledger's mean TTFT and decode speed by `provider/model`, the catalog ref an option carries). Under a search, rows that match equally go fastest first by about how long a 200-token reply takes (`speedRank`), the untimed last, so a model several providers serve lists the fastest one first (axuhere on X). Without a search the rows keep catalog order, grouped by provider. A routing group that always asks the fastest provider is the Speed first strategy ([gateway routing](gateway-routing.md)).
3. **Notice.** After a change the page shows `Notice` when the agent reads its config only at start-up and needs a restart. A field that is `Live` (`Field.Live`: magpie's own setting, which the gateway reads on each request, Claude Desktop's `subagent_model` and `subagent_effort`) needs no restart, so `POST /api/set` and `magpie <agent> <field> <value>` leave the Notice out after it, unless the pick connected the agent too (`Pick` on an agent not connected). A stopped WSL distro's copy of a field keeps the flag (`asleep`).
4. **Drift.** As the Agents page is drawn, `Drift` compares the config with `applied.json`. It runs `Check` first, then each field. An agent pointed at magpie through a reverse proxy is still on magpie (#1985, davisjiahao: a company's nginx at `https://ai.corp.example/magpie`). `wiringOff`, where most agents' `Check` compares a URL, and the checks of their own (Claude Code's managed settings, Reasonix's provider) take a URL that isn't magpie's when it ends with magpie's path, the rest is an http or https address on another machine (`onAnotherMachine`) or one on this machine's loopback with a path of its own (`loopbackWithPath`: the reporter's compliance proxy at `http://127.0.0.1:8788/claude-code-anthropic/<route>`; `proxyBase`), and `GET <rest>/` there answers as the gateway's own `GET /` does (`{"name":"magpie"}`, `magpieAt` in [`reach.go`](../../internal/agent/reach.go), tried in the background like `reachProbe`). Something else there (a relay CC Switch put in) is `unwired`, as is an address on this machine's loopback without a path, which is magpie's on an older port and is never tried. Until the answer is known it isn't drift, so Reconnect isn't offered and doesn't write the proxy away; port moves (`OnGateway`, `Rewire`) re-set only `unwired` agents, so they leave it too. Codex keeps such an address by magpie's key, as for #816 (`codexKeptGateway`: http or https, any port, a path before magpie's, loopback with a path). A model picked in Claude Code keeps it too once magpie has answered there (`surelyMagpie`; `routed` and `gwAt` in `claude.go`), so a proxy every request must go through isn't bypassed; at a relay, a pick points Claude Code at this magpie. Every write to Claude Code (a field's `Set`, `Sync`, `Unwire`) asks such an address first where magpie hasn't answered yet, and waits (`claudeAsk`, `magpieAsked`, as `codexProxyOK` does): unasked, it read as a relay, and the first write in a magpie just started (the CLI's: a pick, the `Sync` a provider added runs, Disconnect) wrote the proxy away, turned the auto mode review back on, or left magpie in and forgot the endpoint the user had. `Follow` writes nothing until the answer is in, and reads never wait. Claude Code's address is asked only while what it sends is for magpie (`claudeProxied`, `claudeKeyed`: a key the gateway takes, or none where it keeps its claude.ai sign-in through magpie): with a key of the user's own it is their endpoint, never asked, and the drift a model of magpie's name there shows says that address, or an administrator's in managed settings, as it is (`whatsOff`; zhangt2333, #3480: magpie sent `GET /` about every 30 s to the `ANTHROPIC_BASE_URL` of a Claude Code it never connected). Tests stub `magpieAt` in `TestMain` as known and not magpie. When the config is right and points at an address off loopback (a WSL twin under NAT, or this machine's Codex at an address the user kept, #816), it tries that address ([`reach.go`](../../internal/agent/reach.go)): in the background, at most every 20 s, never waited for. When nothing answers there while the gateway answers on loopback, the drift is `unreachable` (#1013), with what has to listen there: Share on local network, the user's portproxy, Windows' firewall. Then it checks whether the agent's latest use (`LastUsed`, `Reached`) reached the gateway: a request Codex's log says went to the host its config keeps magpie at, or one the gateway saw from it after (`lastSeen`), reached it.
5. **Disconnect.** `Disconnect` puts back what the stash kept and forgets the record. It also marks the agent disconnected (`<id>.disconnected` in the stash, `Disconnected`) until the user connects it again (`connect`, or an `Apply` that leaves it wired): nothing magpie does by itself puts magpie back in meanwhile, neither a start's `Sync` nor Codex's account failover nor #701's magpie API wiring (paynezhuang on Discord: Codex had `openai_base_url` back after every update). A Codex thread keeps the provider it was started on, so one started while magpie was Codex's provider (its API, or the takeover of a used-up account) still sends to `/v1` after Disconnect or a switch back to ChatGPT. One of Codex's own models asked there that no account in magpie serves (an OpenAI model of Codex's models cache or the catalog), from Codex on this computer with no held gateway key, goes on Codex's own ChatGPT sign-in through `codexBackend`, magpie's key and `x-openai-actor-authorization` left behind (`codexOwnOffMagpie` in [`codex_own_v1.go`](../../internal/gateway/codex_own_v1.go)); it was answered 404 "magpie knows no model" (iuengei on Discord). With the sign-in out of reach (subscription accounts off, signed out, expired) the 404 says why and to start a new thread. `TestCodexOwnModelOnMagpieThreadGoesOnSignIn`, `TestCodexOwnModelOnMagpieThreadStaysHere`, `TestCodexOwnModelOnMagpieThreadSaysWhy`.

## Constraints and failure behavior

- magpie only removes what it wrote. Anything else in an agent's config stays as it was.
- agy's shell function (`update.ShellFunction`, [`shellfn.go`](../../internal/update/shellfn.go)) sits between `# >>> magpie agy >>>` and `# <<< magpie agy <<<`, the only lines magpie writes or takes out of a profile. The profiles are those `cliProfile` names (zsh's in `ZDOTDIR` when set, bash's, fish's `config.fish`), plus PowerShell 7's and Windows PowerShell's on Windows when their execution policy runs a profile. A missing profile is made only for the shell a terminal opens. Only a file inside the home is written, writes go through temp-and-rename, and a profile that can't be read is left alone. Picking one of magpie's models and every `Sync` on one put it there, which covers users wired before it existed. Stepping out and a `Sync` off magpie take it out. agy in a WSL distro gets the function in the distro's own profiles (`agyDistroProfiles` in [`agy.go`](../../internal/agent/agy.go), through `update.ShellFunctionAt`): `~/.bashrc`, `~/.zshrc` and `~/.config/fish/config.fish` where each is, and the profile of the login shell the distro's `/etc/passwd` names (bash when it names none) made where it isn't. The distro's `ZDOTDIR` and `XDG_CONFIG_HOME` aren't read. No magpie runs there, so the function (`agyDistroFunction`) reads `settings.json`'s model with `sed` and carries the gateway's address as the distro reaches it (`place.gw`, Windows' under NAT) and the key it takes from there (`agentKeyAt`, the WSL key under NAT). `Sync` writes it again, so an address WSL changed on a restart follows, and until then `Check` reports a function naming another address. A user's own `alias agy` still wins over it. A terminal opened before the change still needs the `Launch` command.
- A sync brings magpie's models up to date, not where the agent reaches magpie. Every `Sync` that `SyncCatalog` runs (each start and update of magpie, a provider added, and a plugin signed in to, out of or renewed, or listing other models than the last time: `plugin.OnChange` and `plugin.OnListed` call `catalog.Touched`, #2373) goes through `synced`, which passes each file written through `kept.away` (`edit.Filtered`, [`keptaway.go`](../../internal/agent/keptaway.go)). The filter sees every file written through `edit` while it is on, from any goroutine and under whatever lock the writer holds, so it takes none a writer may hold: the gateway's address and the LAN key are read before it is on (`keeping`), and magpie's own files (`magpieFile`: its folder as named or where its links lead, such as a `~/.config` linked into a dotfiles repo) are left as they are (ylorn on Discord: `settings.Save` under the settings' lock reached a filter that read the settings, and the app hung ~10s after every start; `TestOwnWritesDuringASyncWithALinkedConfig`). In a file without the gateway's own address, whose magpie the user pointed at an address on another machine (a NAS's, or this machine's LAN address), and with no address a WSL distro was seen at, that address stays in place of `gateway.URL()`, with the path before magpie's every URL at it had (`awayPath`: a reverse proxy's `/magpie`; on loopback, a local proxy's route where magpie answered or hasn't been asked), and so does the key that went with it in place of magpie's own (coeo91 on Discord: the base URL went back to 127.0.0.1 after an update or restart). An address on this machine's loopback follows the gateway; with more than one address or key gone, the write is left as it is. Picking a model in magpie still points the agent at this magpie, but for Claude Code at a proxy to it (above). ZCode and WorkBuddy keep such an address in their own writers too (`zcodeAddress`, `buddyWriteAt`).
- An agent whose `Sync` does nothing but bring a block of magpie's name up to the catalog is `ListOnly` (OpenCode, MiMo Code and the other OpenCode forms, Pi and its forks, Goose, Crush, Air, AtomCode, Command Code, Droid, Fx, jcode, Kimi, MiniMax, Mothx, omp, OpenChamber, OpenClaw, OpenPencil, Penguin, Qwen Code, T3 Code). `SyncCatalog` runs it only while the agent is connected (`Wired`), as its switch on the Agents page says: a custom provider the user named magpie in the agent, with a few models picked by hand, was written over with the whole catalog at every start (yyddbds on Discord, Xiaomi MiMo; `TestCatalogSyncLeavesAHandWrittenMagpieBlock`). A list magpie wrote while connected waits, while the agent runs a model of its own, until a model of magpie's is picked again; a model of magpie's picked by hand on a provider the user wrote doesn't connect it (`handWired`, above). Every `ListOnly` agent magpie connects reads as `Wired` (`TestListOnlyAgentsReadConnected`). Agents whose `Sync` also repairs while not connected (Codex, Claude, Grok, Hermes' bots) are not `ListOnly`. magpie keeps no copy of a list it wrote over before this, so such a list stays full until the user trims it.
- `SyncCatalog` holds the catalog it builds (`provider.Hold`), the plugins' providers and sign-ins among it, for up to a second. Those `catalog.Touched` drops are told in the background, so a plugin change also drops what is held at once (`plugin.OnChangeNow`, [`hold.go`](../../internal/provider/hold.go)): the host's "auth" event is read before its reply to the sign-in that saved it, and a look at the accounts once the sign-in returns sees it (#2449: `magpie plugin login` found no account while a sync ran; `TestHeldGoesWithAPluginChange`).

## Lody import handoff

[`lody.go`](../../internal/agent/lody.go) detects Lody by its home folder
(`~/.lody`, `~/.lody-oss`) only when it holds an entry Lody makes there
(`workspace-catalog.json`, `loro-repo`, `agent-binaries` or
`code-collab-v2`), so a bare folder of that name another tool made isn't
Lody; by its Electron data folder under the OS's config folder (Lody, Lody
OSS, Lody Nightly: `~/Library/Application Support`, `%APPDATA%`,
`~/.config`); or by a macOS bundle whose id starts `ai.lody.` (the real app
is `ai.lody.desktop`). A Windows or Linux install that has never been
opened has no data folder yet and isn't shown. Its row opens
`lody://provider/import?v=1&data=<base64url JSON>` with the Magpie envelope
and seven runtime targets. Only loopback HTTP gateways are offered; the key
is always the public attribution token `magpie-lody`, never a LAN secret.
With `MAGPIE_ADDR` pinned beyond loopback there is no link: the row has no
button, and `magpie lody add` says why and opens nothing
(`TestLodyLinkCarriesNoSecret`). On macOS and Windows the OS chooses the
installed Lody handler: Lody's bundle and installer claim `lody://`. On
Linux `agent.OpenLody` runs Lody itself with the link, as its desktop
entry's Exec says (`ai.lody.desktop.desktop`, then Nightly's
`ai.lody.desktop.nightly.desktop` and OSS's `dev.loro.lody.oss.desktop`,
in `$XDG_DATA_HOME/applications` before `$XDG_DATA_DIRS`): Lody's AppImage
writes that entry at each start but makes itself the default only for its
channel's scheme (`ai.lody.stable`), so `lody://` reaches it only through
a desktop database that nothing builds without `update-desktop-database`,
and xdg-open's gio answers "Operation not supported" while Lody runs
(Atlas, 10-25). A second Lody hands the link to the running one. With no
entry whose program is there, the link goes to xdg-open as before
(`TestOpenLodyRunsItsDesktopEntry`, `TestLodyImportRunsLodyOnLinux`). The
web page opens the link from the browser and is not covered. A compatible
Lody build must implement this import route.

Lody asks which Providers to add, names them with `-magpie`, and writes only
to the current desktop's local machine after confirmation (Lody 0.108.1:
the import's machine is always the desktop's own, and its link names no
other). So a machine Lody Desktop reaches as a remote, one that runs only
Lody's command-line agent, takes no import from magpie running there:
nothing on it opens `lody://`, and a link opened on the desktop's computer
would point that computer's agents at its own loopback. Lody Desktop
opened on that machine itself shares the agent's `~/.lody/machine-id`, so
the import lands on the same machine (Atlas, 10-25). Magpie does not
read or write Lody's private document store, select models there, or claim
that opening the link completed the import. Lody exposes no public status
reader: `Agent.Added` remains nil and the JSON row omits `added`. The GUI
shows a confirmation hint for this unknown state; Cindy still reports its
known true/false status. `Added` returns `(added, known)`: Cindy's
databases are read without writing beside them (`sessions.OpenUntouched`,
immutable with no WAL log, from a copy with one; a plain read-only open
made `-wal` and `-shm` in Cindy's folder while it was closed), and one that
can't be read, or a stopped WSL distro's, is unknown, never "not added"
(`TestCindyHasClosedWALAndUnreadable`, `TestImportStatusUnreadableIsUnknown`).
Reopening the link lets Lody handle duplicates.
Bub requires its separately installed ACP plugin.

## Whether anything opens an import link

Windows' rundll32, macOS' `open` and xdg-open are started and not waited
on, so an import link that nothing here opens (the app never registered its
scheme, or the program it registered is gone) did nothing at all, and
nothing said so (sungt, 10-29: Cindy's Add magpie on Windows "spins, no
response"). [`applink.go`](../../internal/agent/applink.go)'s
`agent.OpenAppLink` asks the system first, without opening anything:
Windows reads `HKEY_CLASSES_ROOT\<scheme>\shell\open\command` (what
Electron's `setAsDefaultProtocolClient` writes) and then the user's
`UrlAssociations\<scheme>\UserChoice`; macOS asks Launch Services
(`LSCopyDefaultApplicationURLForURL`, cgo builds only); Linux asks
`xdg-mime query default x-scheme-handler/<scheme>`. Only "none", or a
registered program whose full path isn't there, refuses the link with
`agent.NoLinkHandlerError`; a key with no command of its own (a packaged
app's), a bare program name, KDE's empty answer, no xdg-mime, a build
without cgo or a failed read is unknown, and the link is handed over as
before. `/api/open` checks Cindy's, AionUi's and Lody's links this way
(Lody's after `agent.OpenLody`'s desktop entry), and `fail` answers
`code: "no_link_handler"` with `app`, `exe` and `said`, an i18n.js key
from `linkSaid` (the one with ` ({exe})` when a gone program is named),
which `api()` puts through `t()` with the reply's fields, as it does
`bunSaid`'s. The Agents page's import button awaits the call and says what
came of it: "Sent to {name}: confirm adding magpie there" (handed over,
not seen to open), that reason in the reader's language, or any other
error's own text. `magpie <app> add` returns the same error instead of
"✓ opened" (`TestOpenAppLinkSaysNothingOpensIt`,
`TestSystemLinkHandlerNoSuchScheme`, `TestImportLinkNothingOpens`,
`TestLinkSaidIsTranslated`, `TestImportAddSaysNothingOpensIt`,
`import-row.test.cjs`). Whether the app
then shows its confirmation is the app's own and is not read.

## AionUi add-provider link

AionUi (`internal/agent/aionui.go`) keeps its providers in its own SQLite
database, `<userData>/aionui/aionui-backend.db` in WAL mode, with each key
encrypted, so magpie has no file to write there. Its row is the link that
AionUi 2.2.2's main process parses (`parseDeepLinkUrl`) and its renderer
sends to Settings → Model, where the add form opens filled in for the user
to confirm:

```
aionui://add-provider?api_key=<agentKeyAt("aionui")>&base_url=<gateway>/v1&name=magpie&platform=custom
```

`custom` is AionUi's OpenAI-compatible platform, and its OpenAI-compatible
base URLs end in `/v1`. `TestAionUiLinkParsedAs2_2_2` runs the link through
the parser copied byte for byte from 2.2.2's `app.asar`
(`testdata/aionui/deeplink-2.2.2.js`). userData is `os.UserConfigDir()/AionUi`
on every OS. `Added` reads `providers.base_url` for the gateway's address
untouched (`sessions.OpenUntouched`), from the real 2.2.2 schema
(`TestAionUiHas`). It keeps the last read while the database and its log
keep their size and time, for 15 seconds at most. A database it can't read
is unknown. Released 2.2.2 asks for an aionui.com sign-in before any page,
Settings included, so the form, the saved row and gateway traffic have not
been tried end to end. As with Cindy and Lody, the TUI leaves the row out
because there is nothing to pick. `magpie aionui add` opens the link.
