# Provider and plugin ownership

Some built-in subscriptions are deprecated and have community plugins that provide the same service. A subscription can still use its built-in implementation or move to its plugin. That ownership determines where sign-in, refresh, model discovery, requests, usage, and errors are handled.

## Responsibilities and sources of truth

| Part | Responsibility | Source |
| --- | --- | --- |
| Provider migration | Match subscriptions to plugins, record ownership, transfer accounts, and maintain required plugin versions | [`migrate.go`](../../internal/provider/migrate.go) and `migrate_*.go` in the same directory |
| Provider integration | Expose plugin-backed provider cards, usage, sign-in, and the plugin's own daily check-in | [`plugins.go`](../../internal/provider/plugins.go), [`plugin_usage.go`](../../internal/provider/plugin_usage.go), [`pluginsignin.go`](../../internal/provider/pluginsignin.go), [`plugin_checkin.go`](../../internal/provider/plugin_checkin.go) |
| Plugin host | Load plugins and execute their code | [`internal/plugin`](../../internal/plugin), [`host.js`](../../internal/plugin/host.js) |
| Gateway | Dispatch requests through the implementation that owns the subscription | [`internal/gateway`](../../internal/gateway) |
| GUI | Present available subscriptions, migration state, and plugin sign-in | [`app.js`](../../internal/gui/assets/app.js) |
| Community plugin | Implement the moved subscription's upstream behavior | [magpie-community/plugins](https://github.com/magpie-community/plugins), `packages/<name>` |

The `movers` map assembled in `internal/provider/migrate*.go` is the authoritative subscription-to-plugin mapping. Each mover's `min` is the minimum plugin version required by magpie. The list of moved subscriptions in [AGENTS.md](../../AGENTS.md#built-in-subscriptions-that-a-plugin-serves) is a contributor lookup; confirm the mapping in source when changing it.

## Ownership and runtime paths

`provider.Moved(id)` identifies a subscription whose migration state in `migrations.json` is `plugin`. In `/api/providers`, its row exposes `move.state == "plugin"`; the GUI also receives its id in `onPlugins`.

A retired built-in (`retiredBuiltins` in [`migrate.go`](../../internal/provider/migrate.go), `provider.BuiltinRetired(id)`) has no built-in code left: the plugin serves it whether or not a move has run, and its row's `move.state` is `plugin`. Gates that once asked `Moved(id)` ask `provider.PluginServes(id)`, which is moved or retired. Built-in accounts of a retired subscription that haven't moved yet are served by nothing; `/api/providers` lists them in `unmoved` (each a `MoveCandidate`, with the failed move's `error` and `why`), and the GUI shows a line over the Providers list with a Move button (`unmovedLine` in `app.js`). Built-ins are retired one at a time, each in the commit that removes its code.

| Operation | Built-in owns the subscription | Plugin owns the subscription |
| --- | --- | --- |
| Sign-in, refresh, and models | Built-in provider implementation | Community plugin through magpie's plugin integration |
| Upstream requests and translation | Built-in gateway adapter | Plugin fetch through the plugin host |
| Usage and upstream errors | Built-in implementation | Plugin, exposed through magpie's provider integration |
| Migration state and required version | Magpie | Magpie |

For a moved subscription, its built-in upstream implementation does not run. Plugin accounts use `Account.Agent == "plugin"`; requests reach `plugin.Fetch` through `Provider.Do` and bypass the built-in subscription adapter. Magpie still handles routing, protocol conversion, quota handling, and compatibility adjustments, as well as the plugin host, provider integration, migration code, and GUI plugin paths.

Quota aggregation in [`quotas.go`](../../internal/provider/quotas.go) suppresses a key's GLM Coding Plan card only when its comparable reset windows match a ZCode subscription card: built-in or moved `zcode`, or independently installed `zcode-plugin`. [`PlanQuotas`](../../internal/provider/planquota.go) identifies GLM plans by their quota endpoint, including custom provider ids. Matching reset schedules from unrelated vendors do not hide cards. Within this pair, resets remain a heuristic for the shared account; a plan's `User` is a key label or mask, not a login identity. Errors, conflicting resets, or no comparable resets keep the plan visible. This applies to the Usage page, tray, quota reports, alerts, and quota waits; it does not change plugin ownership or upstream requests.

## Usage a plugin collects late

A plugin that learns a step's usage only after the step has ended reports it with a later step, in `usage.magpie_deferred` (`prompt_tokens`, `completion_tokens`, `cached_tokens`, `cache_write_tokens`) beside that step's own usage fields. The Cursor plugin does this: a tool step's usage event shows seconds after the step, so the step says 0 and the conversation's next step collects the event ([#1053](https://github.com/yetone/magpie/issues/1053)).

The gateway parses the field into `Usage.Deferred` ([`cUsage`](../../internal/gateway/chat.go)) and adds it only where it bills: the usage records, the OTel attempt spans and route pricing, which prices it as a tier before the request's own ([`routeUsage`](../../internal/gateway/trace.go), [`Usage.billed`](../../internal/gateway/ir.go)). What a client is told stays the request's own, because agents read `prompt_tokens` as how full their context is: the passthrough forwards the plugin's bytes as they are, whose standard fields are the step's own, and a translated reply is encoded from the own count alone. `promptCounted` also reads the request's own. A reply without the field is handled as before. With an older magpie the field is ignored and the owed step goes unbilled in the ledger. [`deferred_usage_test.go`](../../internal/gateway/deferred_usage_test.go) covers the passthrough, the translated reply, the ledger, the OTel span and the pricing tiers.

## A usage window that says no share

A usage window's `used` (percent) may be left out when the plugin can't tell it: the Loomy plugins send only `display` ([#3650](https://github.com/yetone/magpie/issues/3650)). Left out is not 0. The host passes it on as `null` (`usageOf` in [`host.js`](../../internal/plugin/host.js)), `plugin.UsageWindow.Used` is a `*float64`, and [`quotaOfPlugin`](../../internal/provider/plugin_usage.go) makes such a window `Text` and `Aside`: the card shows its `display` (else "No allowance reported"), never a percentage or a meter (`quotaNoShare` in `app.js`), and `allowanceOf` leaves it out. An account whose windows all tell no share has no allowance, so routing counts it not known (`routedAllowance` in [`routing.go`](../../internal/provider/routing.go), for a fresh reading and the one kept on disk alike), as one never read, rather than as the one with all of it left. A window that says `used: 0` is a reading at 0, as before. [`plugin_usage_absent_test.go`](../../internal/provider/plugin_usage_absent_test.go) and `usage-no-reading.test.cjs` cover both.

A window that leaves out `used` but tells its count, `amount` of `limit` with both above 0, has the count's share (370 of 1000 is 37 used): [`quotaOfPlugin`](../../internal/provider/plugin_usage.go) fills `Used` from it, so the window is neither `Text` nor, unless the plugin set it, `Aside`, and routing reads it ([magpie-community/plugins#468](https://github.com/magpie-community/plugins/issues/468)). Before, such a window was text alone, and an account whose windows all told counts so was unknown to routing. An `amount` of 0 is what a left-out amount reads as, so a `limit` alone still says nothing. `aside: true` keeps a window out of routing (`allowanceOf`) whatever its count; the card and `/v1/magpie/quotas` still show it. `TestAWindowsCountIsItsShare` in [`plugin_usage_absent_test.go`](../../internal/provider/plugin_usage_absent_test.go) covers it.

## A wallet's balance

A prepaid wallet (SuperMagic's points, [#3950](https://github.com/yetone/magpie/issues/3950)) has a balance and nothing it is a share of. A usage window may send `balance` (a number, in `unit`) and leave out `used`, `limit` and `aside`: `{name: "积分", balance: 6291, unit: "积分"}`. The host passes a finite number on, at least 0, and anything else as `null` (`usageOf` in [`host.js`](../../internal/plugin/host.js)); `plugin.UsageWindow.Balance` and `provider.QuotaWindow.Balance` are `*float64`. [`quotaOfPlugin`](../../internal/provider/plugin_usage.go) keeps the figure and does not make the window `Text` or `Aside`, so the account is known to routing with no `Used` invented. `allowanceOf` copies it into `Limit.Balance`, and an empty wallet (0) counts as used up. `Allowance.Left(model)` is the least balance of the windows that count the model, with its unit. `weighRouted` sets `routes.Seat.Left` to it and `Seat.LeftIn` to the account's provider and unit; Smart, `pace` and `usage` put the seat with more left first where they would otherwise tie (`byLeft` in [`strategies.go`](../../internal/routes/strategies.go)), and only among seats that share one `LeftIn`, so balances in two units or two providers are never weighed against each other: each kind is put in the places its own seats take (the pool's order, or what magpie sent each lately for `pace` and `usage`), and the other kinds keep theirs. Before, a pool with two kinds was weighed by no balance, so a group of SuperMagic's and WorkBuddy's accounts spent SuperMagic's smallest balances first (#4095). The card, the Routing page (`Weighed.Balance`) and the CLI show the figure ("6,291 积分 left", `provider.BalanceText`) and no meter. A wallet window's `runsOutAt`/`runsOut` (its soonest batch to lapse) and the rows set aside after it (`aside` text: SuperMagic's day's, timed and permanent points) are display only: the card says them, and the Routing page reads them from the same card (`cardOf` in the routing plugin's `client.js`, live requests only), its row saying the lapse after the figure ("6,291 积分 left · 185 积分 expire 23:59", `runsOutText`, #3964) and its tooltip, and the account list's figure on hover, each window (`winsOf`). Routing goes by the balance alone. Tests: `TestPluginWalletBalanceIsAReading`, `TestPluginHostPassesABalanceOn`, `TestWalletsGoByWhatTheyHaveLeft`, `TestWalletsOfSeveralProvidersEachGoByWhatTheyHaveLeft`, `TestWalletWithMoreLeftGoesFirst`, `TestGroupWalletsGoByWhatTheyHaveLeft`, `usage-wallet-balance.test.cjs`, `routing-wallet-balance.test.cjs`, `routing-wallet-lapse.test.cjs`.

## Cache a vendor doesn't count

A plugin whose vendor counts no cache tokens says so with `usage.magpie_cache_unknown: true` in its Anthropic usage, and leaves the cache fields out. Kiro does this: it caches on its side (a repeated prompt costs about half the credits), but its replies carry credits and a context share, never tokens (opencode-kiro-auth 0.1.16, zeewell on X). The gateway reads the field in [`aUsage`](../../internal/gateway/anthropic.go) into `Usage.cacheUnknown`, ORed across a reply's usage events. [`routeUsage`](../../internal/gateway/trace.go) then sets `RouteUsage.CacheUnknown` on a try that counted no cache read or write. The Routing page's `promptOf` (`plugins/routing/client.js`) leaves such a try out of the hit rate, so the request shows none, not 0%. The field is never told to a client: `Usage.anthropic()` leaves it out, and a passthrough forwards the plugin's bytes as they are. The usage ledger carries it too ([#3464](https://github.com/yetone/magpie/issues/3464)): the gateway records `usage.Record.CacheUnknown` on a call that counted no cache (`Usage.cacheNotCounted`), the ledger keeps it as row flag 8192 (`rowCacheUnknown`), and `usage.Totals` sums such calls' prompt into `cache_unknown` and their count into `cache_unknown_calls`. Every hit rate leaves that prompt out of its denominator: `Totals.HitRate`, and `cacheHitOf` in app.js, used by the tray panel's card, the Usage page's agent rows and cache tile, the requests' Cache hit rate card (which says how many it left out, `cacheLeftOut`) and each ranking row. One of only such calls shows no rate. A request row's cache cells show "—" and its details say the vendor doesn't count the cache. Calls kept before Kiro's plugin said so carry no flag, so a Kiro call (`kiro` or `kiro-plugin`) with no cache counted is read as one (`usage.CountsNoCache`): in the ledger's `rowChunk.row`, in `Totals.countCache`, and for Routing's history in `pricedRoutes` (`cacheCounted`, `internal/gui/trace.go`). The context view (`internal/gui/context.go`, `context.js`) shows no cache for such a call and doesn't score it as a miss. Not covered: hit rates read from agents' own session files (`sessions.Tokens`: the TUI and CLI session lists, the Sessions tab's totals), which carry Kiro's 0 as a miss. [`cache_unknown_test.go`](../../internal/gateway/cache_unknown_test.go) covers the passthrough and translated replies, both whole and streamed.

## A plugin's daily check-in

A plugin can press its vendor's daily check-in (签到) itself: its `auth` hook gains `checkin(getAuth, provider)`, beside `usage`. The host lists the provider with `checkin: true` (`plugin.Provider.Checkin`) and answers `checkin({provider, account})` (`plugin.AccountCheckin`) by refreshing the account as `usage` does and calling the hook with the account's auth.

The hook returns `{outcome, credit?, streak?, message?, until?}`. `outcome` is one of `claimed` (checked in now), `done` (already in today), `ineligible`, `inactive` (no check-in event now), `captcha` or `failed`. A throw, or an outcome not in that list, is `failed` with the reason; for an outcome not in the list the reason names what the plugin answered, before its own message (`the plugin answered "yes": …`), so a plugin's wording isn't read as magpie's. `captcha` means the vendor wants a captcha: magpie never solves one, and says "check in in its own app" instead. A plugin must not solve captchas either. An `inactive` or `ineligible` result with a `message` shows it beside the fixed label ("No check-in event now · <message>") on the card, where it wraps rather than ends in "…", in Settings' check-in line and in `magpie accounts checkin`; the TUI's narrow cell says `c` says why, and `c`'s flash carries it (plugins#304). Without a message the label reads alone.

[`plugin_checkin.go`](../../internal/provider/plugin_checkin.go) runs these through the same `checkiner` as the built-in check-ins ([`checkin.go`](../../internal/provider/checkin.go)): each signed-in, in-use account once a Beijing day, the first look 2 minutes after start and then every 30 minutes, a `failed` asked again after 30 minutes, or at its `until` when that is later (`heldUntil`: a rate-limited claim read, plugins#793), at most 24 hours on and across the Beijing day's turn, a press still asking at once, every other outcome settled for the day. A `done`, `inactive` or `ineligible` answered before noon Beijing (`checkinSureHour`) for an account magpie hasn't seen claim that Beijing day is provisional (`provisional`, #3326): a vendor whose day turns at UTC midnight (08:00 Beijing) or later still answers yesterday's "already" at 00:00, and magpie took it for today's and never asked again. The loop asks it again 30 minutes after the answer, until a claim or an answer from noon on, so at most 24 more asks a day and none once magpie claims; a press (`soon`) asks it again at once, whatever the hour, since the vendor's answer is what the press is for. A claim stamps `Claimed`, carried over while later answers that day say done, so a done after magpie's own claim is settled. Such a record is sent with `again: true` (`shown`, never kept), and the card, Settings, TUI and CLI say the vendor said already checked in and magpie asks again later, not "Checked in today", and the card keeps *Check in now*. A vendor whose day turns after noon Beijing (a US day) is not covered. The Qoder, Qoder CN and ZCode plugins are the exception, as magpie's own Qoder check-in is (`recheck`, `pluginRechecks`, #2696, plugins#503): a campaign or gift plan can open mid-day (Qoder CN's ran 10:00 to 09:59 the next day), so the loop asks again 30 minutes after the last answer, whatever it was but a `captcha` or `own-app`, which waits on the user in the vendor's app and stands for the day (asked again, ZCode's claim only answered 3007 again, plugins#503), and *Check in now* asks at once, and their card keeps *Check in now* for an `inactive` result. Every other plugin keeps the day's result. A plugin whose vendor's day turns at another hour says when in `until` (an RFC 3339 time or epoch milliseconds; `host.js` passes it on as RFC 3339, `plugin.Checkin.Until`), kept as the record's `ValidUntil`: the answer is settled only until then, whatever its outcome (`settled`), the loop wakes then rather than at its next 30-minute look (`wbCheckinLoop.tick`), and an early `done` that says it isn't provisional, since the vendor said when its day turns. Qoder's daily credits open at 10:00 UTC+8 and close at 09:59 the next day (its `/me/campaigns` `startAt`/`endAt`); the Qoder plugins from 0.2.43 answer `until` a minute past the next opening, so a check-in before 10:00, which claims or meets the day before's campaign, is asked again at 10:01, not up to half an hour later (sdytman on Discord). Times are compared as instants, so the machine's zone doesn't matter. Results are kept in `plugin-checkin.json` by `provider|<sign-in key>` (`pluginCheckinKey`: the key `plugin-auth.json` keeps the sign-in under, `autoclaw` or `autoclaw#x1y2z3`), never by the display name: two sign-ins can share a name (AutoClaw's default can't be changed), and keyed by it only the first of them was ever checked in, by the loop or *Check in now* (plugins#254). The sign-in key holds over a refresh and over signing in to the same account again (`settle` in `host.js` puts it back under its key); a sign-in made after one was signed out the same day may take the freed key, and with it that day's result. An entry kept by `provider|<display name>` before then is carried over once the plugin's accounts are listed (`adoptLegacyPluginCheckins`): a check-in goes to the first sign-in in use of that name, the one the old key asked, and only to it, so its namesakes are asked and none twice; an `Off` in `settings.CheckinOff` goes to every sign-in of that name, since none of them was checked in while it was off. A `plugin-checkin.json` that can't be read or parsed is left as it is and carried over once it reads; until then no plugin account is checked in, and each says why (`readCheckins`, as for every vendor's check-in file). A failure is recorded as failed and never resets an account, a key or a previous day's result. Each account's Usage card has the check-in row (`checkinBy: "plugin:<provider>"`), and Settings → Usage has a Plugins tab with a Daily check-in switch per provider (`settings.PluginCheckins`, `POST /api/settings/plugin-checkin {provider, on}`; *Check in now* is `POST /api/usage/plugin-checkin {provider}`). The press says what it came to, a count per kind (`checkinPressSaid`, #3326): claimed now with the credits, already checked in today, not available yet (`inactive`, `ineligible`, or an `again` answer), to check in in the vendor's own app, failed; a result is claimed now only when it carries `asked` (`Asked`, sent but never kept), so an account claimed earlier today counts as already. `magpie accounts checkin` and `c` on the TUI's Usage page include them. Every check-in, built-in or a plugin's, also skips an account listed in `settings.CheckinOff` by its file key (#1902): `checkinNow` asks nothing for it, by the loop or a press, `CheckinAccounts()` lists each account with its own `on` for Settings (`checkinAccounts`, a row each under the vendor's switch when it has two or more, `POST /api/settings/checkin-account {key, on}`), and its card carries `checkinOff`. Under each vendor's switch in Settings, a *Check in now* row checks one account in once (`checkinNowRow`, drawn by [`checkinnow.js`](../../internal/gui/assets/checkinnow.js), loaded when Settings draws a vendor's check-in so it weighs nothing on the core; `POST /api/usage/checkin-account {by, key}`, `provider.CheckInAccount`; xiaowu_95660 on Discord): the same `checkinNow` press, with `only` set to that account's key, so no other account is asked or reported, and the account is asked even while its switch is off, which the press leaves as it is. With two or more accounts the button opens the app menu to pick one. The row says what came of it: checked in with the credit and streak, already checked in today, not eligible or no check-in event with the vendor's message, check in in the vendor's own app, or the failure. It reads the Usage cards again but doesn't draw Settings again under the button.

The switch is off by default. For a provider whose vendor magpie checked in through the plugin's fetch before (WorkBuddy, Trae CN, MiniMax Code, Qoder), it follows that vendor's existing switch until set on its own, and magpie's own check-in leaves that provider's accounts to the plugin (`pluginChecksIn`), so an account is never checked in twice.

Trae CN plugins without `auth.checkin` use [`trae_checkin.go`](../../internal/provider/trae_checkin.go) through the plugin's fetch: `/status`, then `/claim` while the check-in is on and today's isn't in. A claim answered 9074 (当前参与用户太多，请稍后再试) is saved as `own-app`, settled for the Beijing day like any answer other than `failed`: no retry ever got past it (#808), so neither the loop nor Check in now claims again that day, and the card, Settings, TUI and CLI say Trae CN refused the check-in (9074) and to check in in the Trae CN app, not that Trae pays only its own app, which Buddy Switch disproves (#1920). Since plugin 0.2.14 the account this machine's Trae CN desktop client is signed in as sends the client's own device id (the `iCubeAuthInfo://icube-dc:<id>` key of its `storage.json`, read only) with its check-in; every other account keeps its own device, and none is made up or rotated (#1705). 9074 on `/status`, and every other code, keep their previous handling. `own-app` is not a plugin hook outcome.

WorkBuddy's check-in ([`workbuddy_checkin.go`](../../internal/provider/workbuddy_checkin.go), built-in or through the plugin's fetch) tells a 401 apart. WorkBuddy's gateway answers a token it refuses with a bare HTML 401, which the card said only as "Unauthorized" and retried every 30 minutes. On a 401 from `/v2/billing/meter/checkin-activity-status` or `/daily-checkin`, the account's credits (`/billing/meter/get-user-resource-summary`) are read with the same headers: when they read, the sign-in is good and the check-in alone refuses magpie (WorkBuddy's own app sends its check-in, and only that, with an `X-Device-Token` from its security SDK), so it is saved as `own-app` for the day; when they don't, it is `failed` with "sign in to it again".

Qoder plugins without `auth.checkin` still use [`qoder_checkin.go`](../../internal/provider/qoder_checkin.go) through the plugin's fetch. The server's `CLAIMABLE` status decides whether to claim; the local `[startAt, endAt)` check only recognizes an already-claimed campaign and its expiry, including one that crosses Beijing midnight. Successful results keep the active campaign's end in the optional `until` field of `qoder-checkin.json`. Scheduled checks reuse results from the same Beijing day for at most 30 minutes and never past that end, so a long campaign cannot hide new or reset campaigns indefinitely. The existing loop looks every 30 minutes and on a Beijing day change; a midnight refresh saves today's result for the Usage card and TUI. An `inactive` result is now asked again after 30 minutes rather than settled for the day; failures retain their existing retry schedule. A manual check-in always asks immediately. Saved results without `until` remain readable and use the same 30-minute refresh, with no migration needed. Other vendors and plugins with their own check-in retain their daily settlement.

## A plugin's own options

A plugin can declare switches for its provider (#2038): its `auth` hook gains `options: [{key, label, description?, default?, confirm?}]`. The host ([`host.js`](../../internal/plugin/host.js) `optionsOf`) keeps an option whose `key` matches `[a-z0-9_-]{1,40}` and whose `label` isn't empty, drops a key seen before, caps the label at 60 characters and the description and `confirm` at 300, takes `default` only when it is `true`, and keeps the first 16. The provider is listed with them (`plugin.Provider.Options`). An option may give its words in the window's other languages, as a page's `titles` do (plugins#590): `labels`, `descriptions` and `confirms`, each `{"zh": "…", "zh-TW": "…", "ja": "…", "de": "…"}`, kept without what isn't a string or is empty, a language name over 16, or past 16 languages, each capped as the plain one is. `label` stays a string beside them, so an older magpie, which copies only the plain fields, shows the plain words, and OpenCode, whose `AuthHook` is `provider`, `loader` and `methods`, never reads `options` at all. `filtersModels: true` (anything else is false) says the plugin's model list leaves models out while the switch is on, as WorkBuddy's "Free models only" does. `placement: "top"` says the switch is about the whole plugin, not its requests (#5269), and has the editor draw it under the accounts, above Routing; any other value is left out, and the switch goes under the models.

The user's values are kept in `settings.PluginOptions` by the plugin's own provider id and the option's key, and set with `POST /api/settings/plugin-option {provider, key, on}`, which checks the key the same way. The host is handed them at `init` (`options`) and again after each change (`setProviderOptions`, `plugin.SetProviderOptions`, sent only to a host already running). A plugin reads them through `input.magpie.option(provider, key)` (the user's value, else the default; false for a key it didn't declare) or `input.magpie.options(provider)` (every declared key). Both read the current values each time, so a change reaches the plugin without a restart. A plugin written for older hosts checks `input.magpie?.option` first. When an option changes magpie keeps and hands over the value, and forgets the providers it keeps, so they are listed again: a models hook may list by an option (WorkBuddy's "Free models only", plugins#430). Nothing else runs. The check-in switch is separate and unchanged.

The provider's editor lists them under *Plugin options* (`pluginOptionsField` in [`app.js`](../../internal/gui/assets/app.js), the values from `/api/providers`' `plugins[].options[].on`): those with `placement: "top"` in a block right under the accounts, above Routing, the rest in one under the models, each in the order the plugin declares them, and the note that the plugin reads them under the first block drawn. A plugin that says no placement is drawn as before, and an older magpie, which copies only the fields it knows, draws every option under the models. Each is an Off/On beside the plugin's label and description, put in as text, in the window's language (`optionWords`: its `labels`/`descriptions`/`confirms` by the language, then by its first part, so zh-TW reads zh, else the plain one). One with `confirm` asks it before it is turned on. Changes wait for Save, which posts each changed one before the provider. While an option that says `filtersModels` is on, as saved (the list was read with it), the Models field says so under the chips (`pluginFilterNote`): "Only some models are listed: the plugin option “…” is on.", with the option's label in the window's language. Off, or with no such option, nothing is said.

A plugin's package options, the second argument its function is called with (`options` in plugins.json), are a separate thing: numbers and words, not switches. The Plugins page's Installed row has the same *Options* JSON editor for them that a middleware or gateway plugin has (`optionsEditor` in [`plugins.js`](../../internal/gui/assets/plugins.js), `POST /api/plugins/options`, which restarts the host), shown for a plugin that is neither (a provider's, an agent's) when its package suggests options (package.json `magpie.options`, `/api/plugins`' `optionsExample`, now read for every plugin, not only a middleware's) or it has some set; never while it is off (plugins#592: Devin's `cacheKeepaliveInterval` and `cacheKeepaliveMaxPings`, beside its *Cache keep-alive* switch). Its Clear asks "Saved options will be removed…", for every plugin now, not a middleware's words. The Off/On switches above don't get number fields: that would be a new option type across the host, settings and the provider editor. `TestProviderPluginOptionsExample`, `plugin-provider-options.test.cjs`.

## A request a plugin sends by itself

A plugin can tell magpie of a request it sent its vendor on its own, outside any request the gateway handed its `fetch` (plugins#592: Devin's cache keep-alive pings, which re-send the last turn on a timer and were invisible). It calls `input.magpie.usage(provider, {kind, model, input?, output?, cacheRead?, cacheWrite?, status?, ms?, error?, account?})`. The host ([`host.js`](../../internal/plugin/host.js) `reportUsage`) throws a TypeError for a provider that isn't a string of 1–200 characters, a call that isn't a plain object, a `kind` that doesn't match `[a-z0-9_-]{1,40}` or an empty `model`; it makes each count a whole number from 0 (what isn't a finite number is 0; `status` at most 999), caps `error` at 500 characters, and takes `account` only when it is the provider's (`devin` or `devin#…`), else the account of the request in hand (`input.magpie.account(provider)`, `keyFor`), else the provider's id. A plugin reads `input.magpie.account(provider)` while its fetch runs to name, later, the account a timer's request belongs to. It is sent as an unasked `{event:"usage", provider, account, usage}` (`dispatch` in [`host.go`](../../internal/plugin/host.go), `plugin.OnUsage`).

[`plugin_calls.go`](../../internal/usage/plugin_calls.go) registers the one listener and appends a row: agent `magpie`, the provider as magpie names it (`provider.PluginID`), the account's display name (`provider.PluginAccountUser`), the model as both asked and served, its kind, tokens, status, time and error. It is a counted row, as the routing classifier's are, not a probe's: it is priced and in the totals, since the user who turned the keep-alive on is to see what it costs. Its kind `cache_keepalive` is in the purpose catalog as *Cache keep-alive* (`purposeKinds`, `purposes.js`), so the request log names it and can filter by it. It carries no session, so the session views don't count it as a turn. A plugin written for an older host calls `input.magpie?.usage?.(…)`; an older plugin reports nothing, as before. The ping is never routed back through the gateway, which would re-shape the body and break the cache it keeps warm. `TestPluginReportsOwnUsage`, `TestPluginKeepaliveIsCounted`.

## A model's load

A plugin can say how busy each model is (axelburks on Discord: an in-house vendor queues requests to its busy models, and a load put in the model's name changed only when the list did). It calls `input.magpie.load(provider, {"<model id>": 0 and up | null})` whenever it likes, from its own timer, as usage data refreshes; magpie never asks. The host ([`host.js`](../../internal/plugin/host.js) `reportLoad`) throws a TypeError for a provider that isn't a string of 1–200 characters or a `loads` that isn't a plain object, clamps each finite number to 0–10000 (`LOAD_MOST`, `plugin.LoadMost`: past 100 is a vendor that queues, 200 twice what it serves at once, axelburks again; 10000 is a sanity cap), sends `null` as -1 (cleared), drops every other value and an id over 200 characters, takes at most 1000, and sends what is left as an unasked `{event:"load", provider, loads}` (`dispatch` in [`host.go`](../../internal/plugin/host.go)). It returns how many it took.

[`load.go`](../../internal/plugin/load.go) keeps each by the plugin's provider id and the model id lowercased, with when it came (`noteLoads`, at most 1000 a provider). `ModelLoad(provider, model, now)` answers it by the plugin's own id of the model (its callers, the provider editor and `busyOf`, map a model the user lists by another id back through `OwnModelID` first), a model@size falling back to its model, and unknown once it is older than `LoadFresh` (5 minutes): a plugin that stops reporting leaves its models unknown, never idle. Nothing is saved; a restart starts with none known.

The provider editor shows it by the model as a grey badge (`/api/providers`' `models[].load`, `loadTag` in app.js). Routing reads it only when the user sets *Busy models last* (`settings.BusyLoad`, `POST /api/settings/busy-load {at}`, off by default): see `restLast` and `busyBehind` in [gateway routing](gateway-routing.md).

## A search API that uses a plugin's sign-in

A plugin's `search` entry can name one of its own sign-ins with `auth: "<provider>"` (axelburks on Discord: a search plugin reusing a vendor's sign-in had to read plugin-auth.json itself). The provider is one the plugin's `auth` hook signs in to, with models or an auth hook with none. magpie then manages the accounts as it does for that provider's models: it asks the accounts that are on, in the order its model requests take them (a search-rested one last), and the hook's `ctx.getAuth()` returns a copy of the one account chosen, renewed first under `fresh` (the shared de-dup), with the wait counted within the search's time. An account signed out while it is renewed stays signed out, and the search does not go out as it. The hook runs in `inScope`, so a token it saves with `client.auth.set` goes to the account it searched as. A refusal rests that account for search only; the provider's model routing never sees it. Not signed in, or none on, is an error in the request log and in the row in Settings, and the next search API is asked. A plugin with several providers adds an entry per provider. An entry with no `auth`, or one naming a provider the plugin doesn't sign in to, is a keyed search API as before. The search side is in [plugin tools](plugin-tools.md) ("Sign in"); `TestPluginSearchSignsIn` covers it in [`search_test.go`](../../internal/plugin/search_test.go) and [`search_signin_test.go`](../../internal/gateway/search_signin_test.go).

## Where the agent works, for a plugin's fetch

A plugin's fetch runs in magpie's plugin host, so its `process.cwd()` is magpie's own folder, not the folder of the agent that asked. A plugin that tells its vendor the user's environment, as the ZCode plugin's Start Plan request does in its `# Environment` section, said magpie's `~/.config/magpie` as the working directory, and the model went looking there (magpie-community/plugins#86).

The gateway tells the plugin instead. On every request to a plugin's provider, `forwardOnce` calls `tellWorkPlace` ([`workdir.go`](../../internal/gateway/workdir.go)), which reads the request as sent to the plugin with the same `workPlace` that rules by folder use ([gateway-routing](gateway-routing.md)) and sets two headers on the plugin's fetch:

| Header | Value |
| --- | --- |
| `x-magpie-work-dir` (`provider.WorkDirHeader`) | The folder the agent says it works in, percent-encoded UTF-8 (`decodeURIComponent` reads it). |
| `x-magpie-work-git` (`provider.WorkGitHeader`) | `yes` or `no`: whether that folder is in a git repository. The agent's own word beside the folder when it says one (Claude Code's `Is a git repository: true`/`false`, OpenCode's `Is directory a git repo: yes`/`no`), else, when the folder is on this computer, whether git finds a repository from it: the nearest `.git` in it or above it that git takes for one, a folder with a `HEAD` naming a ref or a commit and `objects` and `refs` folders (in the one its `commondir` names, for a linked worktree), or a file `gitdir: <folder>` naming such a folder (a linked worktree's, a submodule's). A `.git` folder git doesn't take, an empty one say, is passed over as git passes it over, so an empty `/tmp/.git` doesn't make every folder under `/tmp` a repository (#3675); a `.git` file that names none is `no`, as git stops there (`provider.GitSaid`, `provider.GitOnDisk` and `provider.GitAt` in [`workplace.go`](../../internal/provider/workplace.go); the library's skill groups find a skill's checkout with the same `GitAt`). |

Each is left off when it isn't known: no folder said, or a folder the agent didn't say is a repository that isn't on this computer or has a `.git` on the way up that magpie can't read (another user's, through a shared magpie). A plugin then leaves out what it can't know rather than saying magpie's. The host's `fetch` (`unsaid` in `host.js`) takes both headers off every request a plugin sends, so a plugin that sends on the headers it was given sends them to no vendor.

`TestPluginToldWhereTheAgentWorks` ([`plugin_workdir_test.go`](../../internal/gateway/plugin_workdir_test.go)) sends Claude Code's and Codex's captured requests and Pi-style ones from a folder in a repository, one not and one under an empty `.git`, through the fake plugin, and checks what the plugin read and that the vendor got neither header. `TestGitOnDiskIsWhatGitFinds`, `TestGitOnDiskAgreesWithGit` (each folder asked of `git rev-parse --git-common-dir` too, beside worktrees and a separate git dir git made itself) and `TestGitOnDiskUnreadIsUnknown` in [`workplace_test.go`](../../internal/provider/workplace_test.go) hold `GitOnDisk` to what git finds, and `GitAt` to the folder git finds the repository in.

## Whether another candidate follows

A free model's vendor may queue a request for minutes: Qoder answers its code 10605 and its plugin waits in Qoder's queue as Qoder's client does (up to 4 minutes), CodeArts answers a 429 with `queue-status: queued` and its plugin polls the trace for up to 5 minutes. While another account, provider or routing group member could answer at once, that wait only keeps the agent waiting (axuhere on X: "模型请求正在排队 · 预计等待超过 10 分钟").

So the try loop marks a try that isn't the last candidate (`withFallback` in [`continuation.go`](../../internal/gateway/continuation.go), from `!last` in the loop), and `forwardOnce` sets `x-magpie-fallback: 1` (`provider.FallbackHeader`) on that plugin request; a header the agent sent under that name is dropped first. The last candidate is never told, and its plugin waits in the queue as the vendor's client does. `unsaid` in `host.js` takes the header off whatever the plugin sends on. `TestPluginToldAnotherFollows` ([`plugin_fallback_test.go`](../../internal/gateway/plugin_fallback_test.go)) sends a group of two members through the fake plugin: the first is told, gives way with a 503, and the second answers untold; a lone model is never told, and the vendor never gets the header.

## Two plugins for one provider id

The host runs one plugin per provider id. When two installed plugins have `auth` hooks for the same id, such as a third-party plugin and the user's own copy added by its folder, `auths()` in `host.js` takes the one picked for that id in `plugins.json`'s `prefer` map (provider id → spec). Without a pick it takes the last one in the list, as OpenCode does. Only the serving plugin's `provider.models` hook runs for that id. Every plugin's `config` hook still runs, so another plugin can still add models or a name to `config.provider[id]`.

Before this, the plugin that lost the id disappeared silently: its row read "Signs in to nothing magpie can use", and `keepUnloaded` could list the id twice, once from the old `plugin-providers.json` (neiko on Discord). Now:

- `init` returns each plugin's `provides` (the ids its auth hooks name) and `servedBy` (id → the other spec, for each id it doesn't serve).
- `plugin.Clashes` turns these into `{id, by, with}` per spec.
- `/api/plugins` gives each row its `clashes`, along with the provider's listed name.
- `keepUnloaded` doesn't keep a provider from before when another plugin serves its id now.

Both rows stay visible on the Plugins page:

- The serving row says "{other} signs in to {name} too; this one serves it".
- The other row says, in amber, "{name} is served by {other}, which signs in to it too". It has a **Use for {name}** button, which calls `POST /api/plugins/prefer {spec, provider}` (`plugin.Prefer`) and restarts the host.

In the CLI, `magpie plugin list` prints the same two lines, and `magpie plugin use <name> <provider>` makes the pick.

How the store handles picks and names:

- Removing a plugin drops its picks.
- Switching a plugin off hands the id to the other plugin until it is switched on again.
- Re-adding a plugin under a new version or spec keeps its picks.
- Remove, off, options and prefer find a plugin by its exact spec first, then by package name (`indexOf` in `store.go`). This way, acting on one plugin never reaches another plugin that has the same package name.

## A plugin that is slow or stuck

The host loads every plugin side by side (`loadPlugins` in [`host.js`](../../internal/plugin/host.js)) and gives each one `pluginLoadWait` (20s, [`host.go`](../../internal/plugin/host.go)) for its import and its plugin function, and each config hook as long. A plugin still loading then is told as not loaded ("the plugin's load didn't finish in 20s") and the host answers `init` with the rest; what it returns later is dropped until the host starts again. Hooks are still kept in the list's order. A listing (`providers`) asks every provider side by side too, and gives each models hook `pluginListWait` (20s, inside `refreshDeadline`'s 30s): one that hasn't answered is listed as fallen back with that as its `listError`, so magpie keeps the list it had, and that answer isn't kept for requests (`keepInfo`). Before, one plugin whose sign-in kept failing held every plugin after it until `init`'s two-minute deadline failed the whole host, and one stuck models hook failed the whole list (shualaitianduai on Discord). `TestStuckPluginLoadHoldsNoOther` and `TestStuckModelListHoldsNoOther` hold both.

## A plugin's 401 about the model

A 401 marks the account's sign-in by default (`notePluginSignIn` in [`plugins.go`](../../internal/provider/plugins.go)), and the gateway fails a 401 over to the provider's next account (`retryable` in [`fallback.go`](../../internal/gateway/fallback.go)), which a model the plan doesn't serve answers the same way. So a plugin that answered "this model isn't available to you" with 401 marked every account of the provider as needing a new sign-in, for credentials that were fine ([magpie-community/plugins#468](https://github.com/magpie-community/plugins/issues/468)). A 401 without `X-Magpie-Sign-In` whose body says the model isn't served (`provider.ModelUnserved`, the gateway's `unservedWords`, read decoded by `catalog.Words`) and nothing of a token, key, credential, session or sign-in (`signInWords`) is now read as `kept` (`modelOnly401`). Only the body's first 64KB is read, and the body goes on whole. The gateway still rests the account under its usual failure backoff for that answer; the guide asks for 403 or 404 for a model the account may not use, which `modelRefused` reads as the model refused. `TestPluginModel401KeepsSignIn` in [`plugin_signin_model_test.go`](../../internal/provider/plugin_signin_model_test.go) covers both kinds of 401.

## A 401 on an access token its refresh token renews

An OAuth account keeps a short-lived access token beside its refresh token, and its plugin's loader (or magpie's `auth.refresh`) renews the access token when its stored `expires` comes. A vendor can turn an access token away before that: Copilot's API dropped the inference token of a slot that had carried no traffic, while its GitHub OAuth token still traded at `/copilot_internal/v2/token`, and the bare 401 marked the account "sign-in has expired — sign in again", whose row then offered only a new device flow ([magpie-community/plugins#618](https://github.com/magpie-community/plugins/issues/618), jinpy666). The host now judges a 401 its plugin said nothing of (no `X-Magpie-Sign-In`) against the sign-in as the request found it (`staleAccess` in [`host.js`](../../internal/plugin/host.js)): an OAuth sign-in with a refresh token whose access token is still the stored one and not due yet is made due (`expires` 1, under the auth lock, only while the access token is unchanged) and said `kept`, so the next request renews it and goes through, and the gateway fails this one over as it fails any 401. The account is still marked when the access token was renewed for this request and turned away, when it was due already and the plugin didn't renew it, when the account has no refresh token, and when the plugin says so (an error with `signIn: "expired"`, a refresh `auth.refresh` was refused). A sign-in that can't be read when the 401 comes (`readAuthState`'s `known` false) is unknown: `kept`, never marked. A marked account is still routed to (`pluginAlsoOn` leaves no account on out for its mark), so a slot marked before is renewed on its next request and cleared by the success. Copilot's plugin 0.1.1 says `expired` only for the token exchange's own 401 and `renewed` for a quota read GitHub answers, which clears a mark left from before. `TestPluginStaleAccessRenewsNotLapses` in [`plugin_stale_access_test.go`](../../internal/provider/plugin_stale_access_test.go) covers the idle account renewed, a renewed token turned away, a refused refresh, an unreadable sign-in and the marked account still routed.

## A sign-in nothing uses

A plugin's `auth.refresh` renews a sign-in only when something uses the account (a request, its models, its usage, its check-in) within its `refreshLead` of `expires`. An account left idle past its token's life lapsed, and for a vendor whose session dies with its token the user had to sign in again: OrcaTerm's WeChat token lives two hours, and its refresh after that answers `SESSION_EXPIRED` for good (#5080, orinsid, [magpie-community/plugins#675](https://github.com/magpie-community/plugins/issues/675)). So the magpie serving the gateway renews each such sign-in as it comes due (`KeepPluginsSignedIn` in [`plugin_keepalive.go`](../../internal/provider/plugin_keepalive.go), started beside `KeepPluginsListed`). It reads the due times from plugin-auth.json (`plugin.RenewAt`: `expires` less the lead the host reckons, `Provider.RenewLead`, listed with `Renews`), asks nothing and starts no host until one is due, and sleeps until the next, at most five minutes. A due sign-in is renewed through the host's own renewal (`keepSignedIn` → `renewal` in [`host.js`](../../internal/plugin/host.js)), the one a request makes: one at a time per account whoever asks, a request arriving meanwhile waiting for the same one, under the lock file every magpie process renews under, through the account's proxy. Only accounts switched on and not marked, of a plugin provider not switched off, hidden (`leftAlone`) or being moved, are kept. A renewal that fails marks nothing: it is held back a minute, doubled each time to half an hour, for that sign-in only; only the plugin's `signIn: "expired"` marks the account, as at a request. A plugin whose renewal costs the account something, or whose refresh token another client holds too, says `auth.keepAlive: false` and is renewed only when used. No plugin in magpie-community/plugins says so as of this change: their refreshes cost no quota, those that rotate a refresh token (Cline, Factory, Nous, SenseNova, CodeArts, Qoder, MiniMax) already rotate it at use, and the ones reading another app's sign-in (kimi-work's reference accounts, Raccoon's desktop) never refresh it. `TestKeepSignedInRenewsIdleSignIns` in [`plugin_keepalive_test.go`](../../internal/plugin/plugin_keepalive_test.go) runs the renewal fixture in a real host; `TestKeeperAsksOnlyWhatIsDue`, `TestKeeperBacksOffAFailedRenewal`, `TestKeeperHoldsWhatTheHostFindsNotDue` and `TestKeptSignInsAreTheOnesSwitchedOn` in [`plugin_keepalive_test.go`](../../internal/provider/plugin_keepalive_test.go) cover the loop and which accounts it keeps.

An account signed out while one of its hooks runs stays signed out. A hook that saves a sign-in through `client.auth.set` (a models list spending a rotating refresh token, as the fake plugin's `rot-` sign-ins do) saves nothing once the account it was called for is gone from plugin-auth.json: `inScope` in [`host.js`](../../internal/plugin/host.js) notes whether the account was signed in when the call began (`had`), and `auth.set` checks it under the file's lock, as `renewLocked` already did for a renewal. A sign-in's own steps (`signingIn`) are not held to it, since their account is new. Before this, a listing that started before a sign-out, or before a failed move took its accounts back out of the plugin (`putBack`), wrote the account in again, and the plugin kept an account of a move that failed (#5126, #5119). `TestSignOutOutlastsRunningHook` in [`signout_hook_test.go`](../../internal/plugin/signout_hook_test.go) holds the hook (`FAKE_MODELS_HOLD`) across the sign-out in a real host.

## How ownership changes

Migration records use five states:

| State | Meaning |
| --- | --- |
| `moving` | Migration is in progress or was interrupted. An explicit retry first rolls back the interrupted move. |
| `plugin` | The plugin owns the built-in provider id. This is the only state recognized by `Moved`. |
| `back` | Ownership returned to the built-in by an older magpie. `MoveRetiring` moves it again. |
| `failed` | Migration failed and the built-in continues serving. Automatic retry waits six hours. |
| `removed` | The user removed the plugin of a moved subscription. Its accounts stay with the plugin's sign-ins and the record keeps them. Nothing moves or installs it by itself; the plugin installed again (`HandOver`) or the editor's Move (`Adopt`) makes it `plugin` again, record and all. |

The editor's "Move to plugin" action calls `provider.Adopt`. With accounts, adoption delegates to `Move`, which installs the plugin, imports every account and commits plugin ownership. Each account is tried through the plugin, and none holds the move back, since the built-in is retired: one the vendor refuses goes along marked lapsed, and one already lapsed or that fails its check otherwise (its vendor unreachable) goes along untried, for the plugin's own reads to judge. No model the built-in served is checked against the plugin's list. Only an install failure, the plugin not serving the id, or a sign-in the plugin won't import fails the move, which then puts everything back (`putBack`) and is tried again after six hours. A `why` from an older magpie's failed move (`lapsed`, `unserved`, `account`) is still read and translated by the page. With no accounts, adoption verifies the package and the provider it serves, then records plugin ownership without account checks.

Installing the plugin independently can also hand over ownership through `provider.HandOver`. The package must be enabled, meet the mover's minimum version, and serve the expected provider. After add, update, or upgrade, the GUI calls `HandOver(ctx, false)`, which can adopt a built-in with no accounts. Existing built-in accounts wait for `HandOver(ctx, true)` in gateway maintenance.

`KeepRetiringMoved` first runs after 20 seconds, then hourly, or sooner when a retired built-in's failed move is due (`nextRetiringRun`). Each cycle maintains moved plugin versions, calls `MoveRetiring`, then performs automatic handover. `MoveRetiring` moves every subscription with a mover (`retiring`, which is `MovableIDs`) that has built-in accounts. A failed attempt waits six hours (`moveRetry`), or ten minutes when the built-in is retired (`retiredRetry`, `retryWait`), since nothing serves those accounts until they move: a move that failed because npm was out of reach or the plugin wasn't installed yet is tried again soon. The built-ins are being retired (the owner, 10-16: 陆续把内置Provider下线掉), so a `back` record is moved again too; a `removed` one is left until the user installs the plugin. Handover turns a `removed` record whose plugin is installed and current back into `plugin`, preserves a plugin already signed in under its separate `-plugin` id and skips existing migration records except a `failed` record old enough to retry.

There is no move back: `provider/moveback` and `magpie plugins move-back` answer that the built-ins are retired, and removing or turning off the plugin doesn't move anything back either. Turned off, the plugin keeps the subscription `plugin`, off with it. Removed (`RemovePlugin`), the subscription is recorded `removed`, its accounts kept in the plugin's auth store, since `plugin.Remove` leaves sign-ins until the user signs out. The Plugins page and `magpie plugins rm`/`off` say the subscription stops working and its accounts are kept. Rolling back a failed move (`putBack`, through each mover's `back` and `settle`) is the only path that writes to the built-in's logins.

Removing a plugin also sets aside the model picks its providers left in `providers.json` (#2057, `plugin_left.go`). Before, nothing listed those records and `magpie provider rm` couldn't find them, so sync and backup asked for a sign-in to them on every run (`NotSignedIn`).

- `RemovePlugin` reads which ids the plugin's providers have (`pluginRecordIDs`: `PluginID` of each provider `plugin.Listed` last gave for its spec, an off plugin's included) while it is still installed. It leaves out:
  - a built-in's id;
  - any id another installed plugin also serves.
- After `plugin.Remove`, only records under those ids that hold picks alone (`OnlyPicks`) move into `providers.json`'s `pluginLeft`, under the package's name. A record with an endpoint or a key is the user's own provider and stays.
- With no listing known (no cache and no readable `plugin-providers.json`), nothing is set aside.
- `provider.AddPlugin` is what the GUI, the CLI and `AddPlugins` (backup and sync) add through. It puts the package's records back, each one whose id has no record now. One the user gave to a provider since stays aside.
- Switching a plugin off sets nothing aside, since off is undone by switching it back on. Records left behind by removals before this change stay as they are; they can't be told from picks a sync brought for a plugin not installed here yet.

New users do not see an unused deprecated built-in in the Add sheet. `unusedSub` leaves it out when it has no account. Until an installed replacement takes ownership, `replacedSub` makes the Add sheet show the plugin tile. The Plugins page is the installation entry point.

`keepMovedCurrent` maintains the required plugin version for moved subscriptions. Raising the owning mover's `min` after publishing a plugin fix triggers this update path. Update failures are logged; disabled packages and local-folder installations are not automatically replaced.

The editor's *Update* button and *Update all* install npm's newest version; a pin the user set is kept until they update it themselves, and is then unpinned. `keepMovedCurrent` is the one path that acts without the user pressing anything, so `installPlugin` leaves what the user chose: a pinned npm version below the move's `min` is not reinstalled, and the move says it is pinned and which version it needs; a git install is reinstalled from its own spec; an unpinned npm one goes through `plugin.Upgrade` (npm's newest, which bun says why it won't install under a `minimumReleaseAge`, where `Add`'s `@latest` would quietly give an older one); a plugin the user turned off is left alone.

A `@magpie-community` package npm doesn't give is installed from the community repo's `dist` branch ([`dist.go`](../../internal/plugin/dist.go)). npm can't take a new package's first version without an owner's 2FA (Trusted Publishing sets up only a package that exists), so reviewed plugins sat unmerged waiting for someone to publish them (magpie-community/plugins#84); a Trusted Publisher made after 2026-09-03 allows stage publish only, and zed 0.1.7 and zen-free 0.1.7 were refused that way. A later install from npm takes its place and `pruneDist` removes the tarballs neither `package.json` names nor `bun.lock`'s `packages` has a package at: Bun installs from the lock's, which can be behind `package.json`, and Bun 1.4.0 writes a package it adds from a tarball into `package.json` a second time, the new tarball first, where `encoding/json` reads the second. A tarball only the lock's `workspaces` names (Bun 1.4.2 and 1.4.3 leave the one replaced there) goes. ## Constraints for fixes

Determine ownership before choosing the fix location. A bug affecting a moved subscription usually needs a change in the community plugin. A built-in-only fix does not reach moved users.

For a plugin fix, publish the corrected community package and raise the owning mover's `min` to that version. Change the built-in too when the fix must reach users who have not moved.

Keep the migration, host, and upstream behavior separate when investigating failures. A plugin bug can require a community change; a host, provider-card, sign-in orchestration, or migration bug can require a magpie change even for moved users.

The host gets magpie's proxy only as `MAGPIE_*_PROXY` and applies it to each fetch itself (`proxyFor`), and to each HTTP/2 session a plugin opens (`http2.connect`, `tunnel`, #1035). A host on the user's own network goes around that proxy as it does for magpie's own requests (`onLAN` in `host.js`, a port of `internal/netproxy/lan.go`'s: a private, link-local, loopback or CGNAT address, a `.local` name, or a name every address of which is one of those, looked up for 400 ms at most and kept a minute; #1572). A provider's own proxy is still taken as it is. The two rules are kept the same: a change to one is made in the other. A program a plugin starts, such as the Grok plugin's `grok login`, gets it back as `HTTPS_PROXY`/`HTTP_PROXY` from the spawn wrapper in `host.js`, unless the plugin set one. A sign-in that works in the built-in and fails through the plugin may be a host difference like this one, not a plugin bug. The same wrapper starts a program that names no folder of its own in `plugin-work` under magpie's config folder (with `PWD` to match), not in the host's own folder beside `settings.json`: the chat page plugin starts the user's MCP servers this way, and a tool's file saved by a relative name, or one named like magpie's own files, landed among magpie's (`TestPluginProgramsRunInTheirOwnFolder`). A folder the plugin gives is kept.

A plugin's fetch is followed through a redirect with its headers only to its own origin (scheme, host and port), or from http to https on the same host: `provider.KeepsCredentials`' rule, which magpie's own requests take (`sent` and `followed` in `host.js`, `sameOrigin` a port of `provider.SameOrigin`; #5508). Bun follows any redirect anywhere and drops only `Authorization` and `Cookie` on a hop to another origin, so `x-api-key`, `x-goog-api-key` and a vendor's own headers went to wherever the `Location` named, and an https vendor's redirect to http was followed. A redirect elsewhere is given back to the plugin as it came, `Location` included, and from a gateway request on to the caller (`Provider.do` hands a plugin's account to its transport, which doesn't follow). A request with no body and only headers any client sends (`BARE_HEADERS`: `accept`, `user-agent` and the like) still follows one anywhere, as a download handed on to a CDN does. A fetch the plugin asks with `redirect: "manual"` or `"error"` is left as it asked. Each hop takes its own proxy (`hop`, `proxyFor`), so a redirect to the user's own network goes direct. At most 10 redirects are followed ("stopped after 10 redirects"); a 307 or 308 whose body is a stream, which can't be sent twice, is the answer. Not covered: `Bun.fetch`, which Bun makes read-only (it skips the host's proxy as well), and a library on `node:http` that follows redirects itself (`node:http`, `node:http2` and WebSocket follow none), #5520.

magpie downloads the Bun build for this machine (`bunTarget` in [`bun.go`](../../internal/plugin/bun.go)): the baseline build on x64 Linux and Windows, the native `bun-windows-aarch64` on Windows on ARM (it was turned away as having no build until #2183), and on a musl Linux such as Alpine (`libc.Musl`, the check Claude Code's download uses too) the musl one, `bun-linux-x64-musl-baseline` or `bun-linux-aarch64-musl`. A glibc build names glibc's loader, which Alpine lacks, so it couldn't start there and exec said "no such file or directory" (#1877). A musl Linux keeps its Buns and their `state.json` under `bun/musl`, so a machine whose C library changed never runs the other one's build or takes its set-aside versions; everywhere else they stay in `bun`, where a Bun downloaded before is. A bun that is on disk but can't be started says it is a build for another C library and names `MAGPIE_BUN` (`cantStart`), and it isn't fallen back from or set aside: the version before is the same build. Bun's musl build needs libstdc++ and libgcc; on an Alpine without them, `bun add` and the host's start say which library is missing and `apk add libstdc++ libgcc` (`missingLibs`). `TestBunTargetForMusl`, `TestMuslBunKeptApartFromGlibc`, `TestCantStartSaysCLibrary`, `TestHostOnUnstartableBunSaysCLibrary`, `TestMissingLibsNamesThem` and `TestHostOnBunLackingLibsSaysWhich` in [`bunmusl_test.go`](../../internal/plugin/bunmusl_test.go) cover these.

A bun this machine can't run at all says so instead of its exit status (`wontLoad`, a `*BunUnstartableError`). Windows refuses to load Bun 1.3.14 and later before Windows 10 1809 and Windows Server 2019: they import kernel32's `CreatePseudoConsole`, which older Windows lacks, so the process ends with 0xc0000139 (STATUS_ENTRYPOINT_NOT_FOUND) before it runs (zgcwkj on Discord, a Windows service). A processor without an instruction Bun's x64 build uses (it targets SSE4.2) ends it with 0xc000001d on Windows and SIGILL elsewhere. `bun add`, `bun update` and the host's start (`whyDied`, `cantStart`) each wrap the exit in it. The message says which of the two it is and names `MAGPIE_BUN`. An install doesn't try the community repo's dist branch after it, because that `bun add` can't start either. The GUI's `fail` answers it with code `bun_unstartable`, `bunWhy` (`windows` or `cpu`) and `said`, the i18n.js key for it (`bunSaid` in api.go, kept there so app.js holds one line under its budget), which `api()` in app.js puts through `t()` in place of the English. `TestBunSaidIsTranslated` fails when a language lacks it. There is no fallback to an older Bun: the last one Windows Server 2016 loads, 1.3.13, is below `BunVersion`, and Bun's baseline assets are now the same binary. `TestWontLoadSaysWindowsOrCPU`, `TestInstallOnUnstartableBunSaysWhyAndSkipsDist` and `TestHostOnUnstartableBunSaysWhy` in [`bunload_test.go`](../../internal/plugin/bunload_test.go), `TestFailSaysBunUnstartable` in internal/gui and `plugin-bun-unstartable.test.cjs` (both engines, every language) cover these.

Bun takes only http:// and https:// proxies. A SOCKS5 one, such as a Mac's system SOCKS proxy, is given to every bun magpie starts as a loopback HTTP proxy in front of it (`netproxy.Bridge`): to the host through `hostEnv`, and to `bun add`, `bun update` and `bun remove` through `bunCommand` (`netproxy.EnvForBun`). Before, an install with only a SOCKS system proxy failed as `UnsupportedProxyProtocol` (#1409). An agent CLI that bun installed is updated through the bridge too (`updateEnv` in `internal/agent/cliupdate.go`). Claude Code, built with Bun, gets it for the Claude subscription's runs and sign-ins (`netproxy.EnvForBunWith`, #2651; see [Claude subscription bridge](claude-subscription-bridge.md)).

The host reads its proxy once, when it starts. When the proxy magpie would give a new host differs from the one the running host got (the system proxy set after magpie started, as at login before Clash is up, or Settings changed), the next call to the host replaces it (`proxyMoved` in [`host.go`](../../internal/plugin/host.go), looked at no more than every 15s, or every 2s while the host has no proxy: `proxyLookNone`, #1518). A call made for a read nobody asked for, while allowances are read only when asked (`netproxy.Held`), never reaches the host. Before this, a host started without a proxy kept none, so the Grok plugin's `grok models` couldn't renew its token and the account read as signed out after each restart (#1363).

The host is told where magpie's gateway is as `MAGPIE_ADDR` (`hostAddr` in [`host.go`](../../internal/plugin/host.go)): magpie's own `MAGPIE_ADDR` when it runs under one, on loopback when that listens on every interface, else Settings' port on loopback. A plugin with a service of its own reaches the gateway there; Magiczerowxy/magpie-chat's chat server asks `MAGPIE_ADDR`, then 3425, so with the port set in Settings its model list was empty (Magiczerowxy/magpie-chat#1). A port changed in Settings is a new host's at the next call, as a moved proxy is (`proxyMoved`), and opening a page whose plugin has a host part is such a call (`plugin.Warm`). Test: `TestHostToldTheGatewayAddress`.

What a plugin writes with `console.log`, `console.warn` and the rest goes to the host's stderr, which magpie logs a line at a time (`drainStderr` in [`host.go`](../../internal/plugin/host.go)). A line over 4 MiB ends the logging: magpie logs that it did, and reads and drops the rest, so the host never blocks on a full pipe. Before, nothing read the pipe after such a line: on Windows the host hung on its next write, and on Linux Bun kept everything written after it in memory.

The host is waited for the moment it ends, not when its stdout reaches EOF (`reap` in [`host.go`](../../internal/plugin/host.go), `proc.Output` in [`output.go`](../../internal/proc/output.go)). A program a plugin started that kept a copy of the host's stdout (a `Bun.spawn` given `Bun.stdout`, a daemon it left running) held that pipe open past the host's end, so the reader never saw EOF, the only `cmd.Wait` never ran, and every host stopped (a restart, a moved proxy) stayed a `<defunct>` magpie-bun under magpie until it quit (acezan on Discord, a Linux systemd service). Once the host has ended, the reader has `proc.OutputGrace` (2s) to read its last lines; then its stdout and stderr are closed under their readers and the host fails as one that quit. Every command magpie starts elsewhere is waited for too: one it leaves running goes through `proc.StartReaped`, never `Process.Release`, which doesn't reap on Unix (`TestEveryStartedCommandIsWaited` in [`reap_test.go`](../../internal/proc/reap_test.go)). `TestHostReapedWhileItsChildHoldsStdout` (Linux) runs a real host whose plugin holds its stdout that way and counts this process's `<defunct>` children after each Restart. Before `magpie web` puts a new version in its own place (`Web.Wait`, `update.Reexec`), `plugin.EndHosts` stops every host, waits until each has been waited for, and starts none after: a host still running at the exec is a child nothing waits for after it, one `<defunct>` magpie-bun per restart to update (#3285; `TestEndHostsLeavesNoChild`). The host is started as a `proc.Tree` (`Output.StartTree`): a session of its own on Unix, a job on Windows. Every way a host ends (`stop` after `stopWait`, a line too long, the host ending by itself) ends what its plugins started with it, at any depth: `host.kill` kills the tree, and the wait sweeps what a host that ended by itself left. A host killed alone left a plugin's headless Edge processes running with no parent (Bun's own job lets a child's children out of it on Windows), 620 msedge.exe in an hour on one machine (#5402, baijiu666). Nothing outside the host's session or job is reached, magpie's own process group included. `TestHostEndedEndsWhatItsPluginStarted` runs a real host whose plugin starts a child that starts another, on each of the three ends.

A plugin's account whose sign-in its vendor refused (`lapsed`, or an allowance read saying so) keeps Sign in again and Remove on its row, whether it is in use or the agent's own (`signedOut` in `renderAccounts`, `app.js`).

A plugin sign-in's page is opened once. An `authorize` result may say `opened: true` (not OpenCode's field): the plugin's own CLI opened the page already. Grok's `grok login --device-auth` does this on macOS and Windows, where nothing turns it off, and magpie's opening it too showed two pages (andyfmyth on X; plugin 0.1.17, which on other systems gives grok a `BROWSER` that opens nothing instead). `host.js` passes it on as `Authorization.Opened`, then `SignInState.Opened`, and the desktop's `/api/plugin-signin`, `magpie plugin login` and the window in a browser tab (`startPluginSignIn`, and `followSignIn` after an install) then open nothing; the page's link is still shown (`TestPluginSignInPageOpensOnce`, `plugin-signin-opened.test.cjs`).

A plugin sign-in magpie gives up on ends in the host too (#5016). The user's Cancel, or the sign-in's timeout (`signInTimeout`), ends `plugin.Finish`'s context, and `authorize`, `callback` and `apiKey` are cancellable calls (`cancellable` in [`host.go`](../../internal/plugin/host.go)), as a gateway request is: magpie writes `abort` for the call, and `host.js` (`signInSteps`) drops whatever the plugin answers after it, so nothing is saved, and counts the call as done at once. The plugin's own wait is told where the host can tell it: every fetch the plugin makes for the sign-in carries the sign-in's signal (`whileSigningIn`), and magpie's hook hands the signal to the plugin as a second argument, `callback(code, { signal })` and `authorize(inputs, { signal })` (OpenCode passes none), so a plugin that polls a file or its vendor for minutes (AStudio's waits on its desktop app's session file, plugins#658) can stop. Before, a session file written after Cancel still signed the account in. An `oauth` method's `authorize` that can't start says why as an `api` method's does, `{ type: "failed", error }`; `host.js` answers it, or a result with no `callback`, as the sign-in's failure (`plugin.Authorize` gives `ErrFailed` with the reason) instead of calling the callback it lacks, which reached the user as "s.a.callback is not a function". `TestCancelledSignInSavesNothing`, `TestCancelledSignInEndsThePluginsWait`, `TestCancelledSignInEndsItsFetch` and `TestSignInFailsWithThePluginsReason` in [`plugin_signinend_test.go`](../../internal/plugin/plugin_signinend_test.go).

Every other call but `init` is cancellable too (#4678): a models list, a usage read or a check magpie stops waiting for (its caller left, or `listWait` ran out) gets an `abort`, and `host.js` aborts the call's signal, which the usage hook gets as `usage(..., { signal })` and the models hook as `signal`. The call stays pending in the host until its handler ends, and nothing it answers after the abort is sent, so a hook still saving a refreshed sign-in finishes before the host may exit. `TestCancelledCallKeepsTheHostTillItsHookEnds` and the other tests in [`plugin_rpc_cancel_test.go`](../../internal/plugin/plugin_rpc_cancel_test.go).

The GUI's plugin integration includes `subOf`, `pluginSubs`, and `startPluginSignIn`. A change to sign-in or provider presentation must follow these paths as well as the built-in paths it affects.

Run the relevant package tests with an isolated home directory. Resolve GOPATH and Go's caches before changing HOME, so repeated runs reuse dependencies and downloaded toolchains. The subshell makes temporary files writable and cleans up its home on exit, including when tests fail, and returns the test command's exit status.

```sh
(
	verification_home=$(mktemp -d) || exit
	trap 'chmod -R u+w "$verification_home"; rm -rf "$verification_home"' EXIT
	verification_gopath=$(go env GOPATH) || exit
	verification_modcache=$(go env GOMODCACHE) || exit
	verification_buildcache=$(go env GOCACHE) || exit
	HOME="$verification_home" GOPATH="$verification_gopath" GOMODCACHE="$verification_modcache" GOCACHE="$verification_buildcache" \
		go test -tags nogui ./internal/provider ./internal/gateway ./internal/plugin
)
```

Some migration and gateway plugin tests require Bun on PATH and use local plugin fixtures; they skip when Bun is unavailable. Report any skipped tests and verify the community package separately when its implementation changes.

### Fixed-credential sign-in

An `auth.methods` API method may declare magpie-only `keyless: true` when
its `authorize` function supplies the credential. The host carries this
boolean only for API methods with an authorize function. GUI and CLI skip
personal-key entry for it; ordinary API methods still require a key.
`auth.single: true` declares one provider identity: signing in again reuses
its account slot and the account action says Sign in again. Existing records
are not deleted. Other plugins keep multiple accounts. OpenCode ignores
these optional fields; no provider id is special-cased in magpie.
