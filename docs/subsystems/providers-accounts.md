# Providers and accounts

The gateway can send a request to three kinds of upstream:

- A **provider** in `providers.json`: an endpoint with one or more API keys. Google Vertex AI's has no key: it is signed with the user's Google credentials.
- A **subscription account**: an agent's own sign-in (Codex, Claude Code, Copilot and others) that magpie reads from the agent's store, or an account signed in from magpie.
- A **plugin's account**: a subscription served by an OpenCode plugin.

Package `internal/provider` holds all three, the routing groups built over
them, and what is left of each one's allowance.

Plugin ownership of the deprecated built-in subscriptions is in
[Provider and plugin ownership](provider-plugins.md). How the gateway orders
keys and accounts per request is in [Gateway routing and fallback](gateway-routing.md).

## Remote magpie

The `remote-magpie` preset is of its own kind, `KindRemote` (`remote`), not
a relay: the app's Add sheet lists it under Another computer's magpie, after
On this machine, and `magpie presets` and the TUI's add list name it so too
(`kindNote` in [`tui/pages.go`](../../internal/tui/pages.go)).

A `remote-magpie` provider derives Chat, Responses, Messages and System One
bases from one address (`remoteMagpieEndpoints` in
[`remote_magpie.go`](../../internal/provider/remote_magpie.go)). Its model
list requests images, videos and decisions with `X-Magpie-Drawers`,
`X-Magpie-Videomakers` and `X-Magpie-Deciders`. The gateway includes these
only when asked, with `kind` of `image`, `video` or `decision`. Any other
client asks for image and video models with `?kind=` (`chat`, `image`,
`video`, comma separated, or `all`; `listKinds` in
[`gateway.go`](../../internal/gateway/gateway.go)); without it the list is
chat models alone, so no agent's chat picker offers an image or video
model, and an unknown kind is a 400 (axelburks on Discord;
`TestModelsListMediaOnlyWhenAsked`). Decision
entries pass through `keyAllowed`, including model and account restrictions.
[`catalog/live.go`](../../internal/catalog/live.go) keeps each kind and all
models the remote already exposed, including retrieval models. The shared
list has no separate retrieval kind: these entries remain in `Catalog` and
agent model lists, just as on the remote. Keeping them makes retrieval
routing possible; their presence does not mean they support conversations.

`DecidesModel` uses the remote's explicit decision marker, so Clef and custom
names work and a chat model named Jev Router stays a chat model. `Deciders`
lists, and the gateway answers, these decisions even when the user's local
conversation picks omit them. What a routing group's pickers, templates and
the TUI offer is `OfferedDeciders`: with picks saved, only the picked
decision models plus any a group names already, as the provider editor
shows the rest unpicked (coeo91 on Discord: two free OpenRouter models
picked, OpenRouter's decision models still offered beside them). Only remote decision entries use `entryFor`
to apply user model names and limits; other decision providers retain their
previous entry formatting. The editor's `providerInfo` in
[`providers.go`](../../internal/gui/providers.go) sends `deciders: []` when
the remote has none, suppressing the UI's legacy name-based guessing.
The editor offers one remote address; its System One endpoint is derived
from that address and has no separate input. Unnamed decisions use their
model ids for display names and provider labels.
Refresh replaces the list: removed decisions stop routing, and an empty
remote list never gains a fabricated Jev alias.
An older peer without the decision-list extension continues serving its
other APIs but must be updated before its decisions can be discovered.
See [`decide.go`](../../internal/provider/decide.go).

oMLX (#1641) and MLX-Serve are such mixed providers too: oMLX's server lists
Clef, Clef-Flash and OpenJev among its chat models with nothing to tell them
apart, so its decision models are the ones its `/v1/models/status` gives
`model_type` `decision`, by the name `/v1/models` uses (its alias), kept under
`<id>.decisions` like OpenRouter's (`omlxDecides`, `listedOMLXDecide` in
[`omlx_decide.go`](../../internal/provider/omlx_decide.go)). MLX-Serve marks
them in its `/v1/models` with `capabilities: ["decisions"]`, kept under
`<id>.decisions` (`mlxServeDecides`, `listedMLXServeDecide` in
[`mlxserve_decide.go`](../../internal/provider/mlxserve_decide.go)). Ollama
and Ollama Cloud (Nanka on Discord; Ollama 0.35.0+, 0.40.5+ for cloud models)
serve System One at `/v1/systemone` beside their chat API, and list decision
models (Tev, Nimble, Clef) in `/v1/models` like any other. Their `/api/tags`,
asked with the same key, gives each model `capabilities`, `decision` for
these and `vision` for one that reads images. Those are kept under
`<id>.decisions`, with the cloud's 65,536-token window when the list gives
none (`ollamaDecides`, `listedOllamaDecide` in
[`ollama_decide.go`](../../internal/provider/ollama_decide.go)). An Ollama
older than its System One lists no capabilities, so none. A server
with none lists none, and no Jev is made up for it. An oMLX, MLX-Serve or
Ollama provider saved before the preset had a decision base gets its chat
base as one.

The CLI and TUI report model-list fetch errors for remote and other mixed providers
(such as OpenRouter, serving conversation and decision models). Only a
decision-only provider keeps the separate decision discovery behavior
(`announce` in [`providers_cli.go`](../../internal/cli/providers_cli.go), `addKeyAsk` in
[`pages.go`](../../internal/tui/pages.go)). A remote's endpoint test reuses
successful model discovery for its decision result, and reports none when
no decision model was discovered (`Test` in
[`test.go`](../../internal/provider/test.go)).

Account discovery can be turned off (#1535): Settings → Privacy → *Subscription accounts*, `magpie accounts discovery off`, or `MAGPIE_NO_ACCOUNTS=1` for one process. The first two save `noAccountDiscovery: true`, which this computer keeps through a sync or a restored backup (`KeepOwn`); the variable only ever turns discovery off, never on what the user saved off (`settings.AccountDiscoveryOff`). It is on by default. In the GUI, Off asks first and names the subscriptions in use that it stops (`discoveryOffWarning` in `app.js`, #1761: a user turned it off without meaning to and was left with no subscription working). While it is off, magpie reads no agent's sign-in: no credential file (`~/.claude/.credentials.json`, `~/.claude.json`'s account, `~/.codex/auth.json` or Codex's keychain item, Copilot's, Cursor's, Devin's, Kiro's, Gemini's, ZCode's, Command Code's, OpenCode's `auth.json`), no Keychain or Secret Service item (`security`, `secret-tool`), and no agent CLI asked who is signed in. ## Runtime path

1. **Add.** The Providers page adds a key provider through `Add` or `Save`, or an account through `StartSignIn`. An agent signed in on its own is found by `Accounts` with no step from the user.
2. **Resolve.** The gateway calls `provider.Resolve` or `GroupFor` with the model name, then plans candidates over the provider's keys or accounts.
3. **Sign.** For each try, `Sign` gives the request its auth. A token about to expire is refreshed first, and the rotated tokens go back to their one holder: the agent's store, or `logins.json` for an account standing behind it.
4. **Allowance.** Usage endpoints are rate limited, so `SubscriptionUsage` caches its results: a cached copy comes back at once and a stale one is refreshed in the background. When an account's windows start again, `OnRenewed` tells the gateway so a resting account can come back: a Codex reset spent (`renewedNow`), or a reading routing takes (`Allowances`, as the agent the account's usage is read under, `claude` or `plugin:<id>`) that finds the account full till sooner than the last did (`renewedFrom`, the rule a key's reading goes by): the whole account, or a pool of some models with the whole account's windows over it. A window used below `SpentShareOf` its routing, or whose reset passed, is full no more; one full with its reset not known is full for good. A Claude account is back as soon as a new `/usage` or the reset passing shows the window it was out of started again, not when the time Claude Code's refusal named comes; its five hours started again in a week used up tells nothing. A first reading, a failed one, one read alike, or one leaving the full window out tells nothing, and a reset spent is told once, by `renewedNow`. A key's reading that finds a window it was full in (at `SpentShareOf` its routing) full no more, or full till sooner, tells it too, as agent `""` and the key's `KeyAllowanceID`, so a key out of its limit is back once the limit is raised or its usage reset; a first reading, a failed one, or one that finds it fuller tells nothing. An account refused for its quota has its agent's allowances read again at the next ask (`StaleAllowance`). A reading already out then was asked before the refusal: what it read is kept, as not read, so the ask after it lands reads again, as `StaleKeyAllowance` does for a key.

## Constraints and failure behavior

An allowance deliberately not requested (a saved Claude account outside
its card refresh, or allowances set to *When I ask*) can use the last
reading with `readDeferred: true`. `AsOf` and `ReadAt` still date that
snapshot; the GUI says it was not refreshed this time rather than that a
request failed. Network failures, unavailable `/usage` and account refusals
are not deferred reads. The flag also reaches `magpie quota --json` and
the gateway report. [`quota_last.go`](../../internal/provider/quota_last.go),
`TestQuotaDeferredReadIsNotFailure`.

Allowance readings are kept by provider, lowercased account and window in
`quota-history.json` ([`quota_history.go`](../../internal/provider/quota_history.go)),
for up to 45 days and 6000 points per window. Failed or stale readings add
nothing. A window set aside for routing is kept when it is measured (a
pool's window, or the Cursor plugin's Weekly and Grok Bot, #4612); a
text-only one tells no share and is not, and neither is a plugin's aside
window that leaves `used` out with no count to reckon one from: its `Used`
is 0 for want of a share, not a reading, and drew a flat 100%-left line
(`noShare`, #4825). `newCycle` preserves a boundary
when the previous deadline passes,
appears/disappears, moves backward by more than five minutes or forward by
more than the elapsed sampling time plus five minutes. A refill of more
than five percentage points with a deadline unchanged within five minutes
is also a boundary: a manual or vendor reset need not change the deadline.
Smaller corrections and a rolling deadline advancing with time do not
split that window. These are observed boundaries, not a record of who reset
it; multiple resets between readings and refills hidden by subsequent
spending cannot be recovered. Sampling compression and sync merging keep
readings on both sides of detected boundaries.

Whole-window estimates in [`window_holds.go`](../../internal/usage/window_holds.go)
leave out a window whose calls fall in one of the account's dry runs, since a
call answered there may have been paid from credits or extra usage (#2010,
NorethSea). A known vendor reset ends a dry run, even when the next poll sees
the refill later, and a following dry run starts no earlier than that reset,
so calls between the two still count. A reset time that isn't known keeps the
run open. A stale dry reading taken after its own reset can't extend a run.
Credit balances are read account-wide and shown rounded, and the ledger has no
per-request credit charge. Comparing two balances can't tell which concurrent
or outside call spent credits, so no per-call attribution is attempted.
A refill observed later than reset minus span (`QuotaPoint.StartsCycleAfter`,
the same boundaries history sampling keeps) starts what is reckoned, so calls
before a fixed-deadline refill stay in the cycle before it. The card's window
keeps its span, so its Pace is the vendor's (`withSpansOf`). A first reading
with no recorded start is not a reset. `HistoricalWindowHolds`
([`window_holds_history.go`](../../internal/usage/window_holds_history.go))
reckons a past cycle's windows the same way, each at its own last reading in
the range, with that reading's percentage and bounds, the cached card's model
scope, and only calls and readings before that reading. A card that is gated
live (a balance, a remote, an error) is gated for past cycles too, and a
window no longer on the cached card is left out. Past prices aren't kept, so
the cost is at today's API list prices. A call whose own id has no API price
is costed as the model the reply named (Served), as the ledger is (#1498). See
`TestWindowHoldsDryAgainAfterReset`, `TestWindowHoldsUsesObservedRefillStart`
and `TestHistoricalWindowHoldsUsesEachWindowsOwnReading`.

- A streamed turn to the ChatGPT backend (POST `CodexBase`/responses with `"stream":true`) goes over the backend's WebSocket, as Codex's own client sends it, and comes back as the server-sent events the HTTP route answers with (`codexSocket` in [codex_socket.go](../../internal/gateway/codex_socket.go), first in the gateway's `upstreamTransport`, so Codex's own sign-in passed through and magpie's ChatGPT accounts both take it, through the proxy in force). On some networks a streamed HTTP reply from chatgpt.com is cut at about 120 s, before `response.completed`, while the WebSocket runs to the end (brickhao on Discord). The handshake carries the turn's headers with `OpenAI-Beta: responses_websockets=2026-02-06`, without `x-codex-turn-state` and the responses-lite header, which go in the message's `client_metadata` as Codex puts them; the message is the body with `"type":"response.create"` ahead of it (a zstd body is decoded first). `codex.rate_limits` and `codex.response.metadata`, read ahead of the reply, are also told as the `x-codex-*` and `x-codex-turn-state` headers the HTTP route carries; `responsesapi.websocket_timing` is dropped. An `error` frame ahead of the reply is that status with its error as the body; `websocket_connection_limit_reached`, a refused handshake or a body that isn't a streamed turn goes over HTTP instead, and a host that refused the handshake (other than 401, 429 or 5xx) is spoken HTTP for 10 minutes (`codexSocketShun`). A socket that ends, or won't take the message, before any frame of the reply was handed on (any close status, a dropped connection, a normal close with no reply) sends the same body over HTTP (`codexSocketEnded`): Lamrfu's long conversation was closed 1009 (message too big) by chatgpt.com and got a 502. magpie opens a socket per turn and sends the whole body, where Codex's own client sends a delta after `previous_response_id` on a kept socket. A message at least as big as one a host closed 1009 goes to it over HTTP for 10 minutes (`codexTooBig`). A socket closed after the reply began reads as a cut stream (`io.ErrUnexpectedEOF`), and is not asked again. Codex speaks to magpie over its own WebSocket since #4058 ([A Responses WebSocket](gateway-routing.md#a-responses-websocket)), sending a turn as a delta after `previous_response_id`; magpie gives each turn the whole conversation before it goes on, so this leg still sends the whole body. How a pool ends at its caps is kept with the provider (plugins#349): `CapStop` answers 429 rather than going on to the fallbacks once every account in use is at its cap, and `CapCareful` reads usage again near a cap and holds an account whose usage can't be told (both off by default; within 5 points of its cap an account takes one turn at a time whatever they say, [gateway routing](gateway-routing.md); `SetCapStop`, `SetCapCareful`, GUI `provider/capstop` and `provider/capcareful`, ticks under the account list once an account has a cap). `UsageRead` says when an account's usage was last read well and whether the last try failed (a failed try keeps the good reading's time), and `ReadUsageNow` reads it again. `magpie provider pool <id> [--accounts a,b,…] [--cap percent|off] [--stop on|off] [--careful on|off]` shows and sets the whole pool in one command: which accounts are on and in what order, each one's cap, and both settings, and names the accounts in use with no cap.
- A key's spend cap (`KeySpendCaps`, by the key's fingerprint, [`key_spend.go`](../../internal/provider/key_spend.go); sparkling_lemur_62868 on Discord: a team's OpenAI key whose granted credits other services spend from too) is how much magpie may spend on an API key, in USD, per calendar day or month in local time, or in all since it was set (`Since`, kept while the cap stays one in all, its amount changed or not). What counts is what the Usage page prices magpie's own calls on the key at (`usage.KeySpent`: records whose `ProviderKeyID` is the key, not turned away, not reported by an app; the log is read once and each new call added by `Append`, read again after 5 minutes), not the vendor's bill: a model with no known price counts nothing, and requests under way when it is reached still finish, so the key can go a little past it. At or past the cap the gateway passes the key over ([gateway routing](gateway-routing.md)). Only a key has one: `SetKeySpendCap` refuses a subscription, an amount not above 0 or over `MaxSpendCap` (1,000,000) and a period it doesn't know. `ReplaceKey` carries it to the new value. Set from the key's row in the editor (a pill: "$7.50 of $20.00 today", the app's menu, then the amount typed in place, drawn by `keyspend.js`, which app.js imports when it draws a key's row; GUI `provider/keyspendcap`, `key-spend-cap.test.cjs`) or `magpie provider spend-cap <id> [key [usd [day|month|total]|off]]`, which also lists each key's spend. `TestKeySpendCapSet`, `TestSpendCapWindow`, `TestParseSpendCap`, `TestKeySpentCountsTheKeysCalls`, `TestSpendCapCmd`.
- A window whose reset time has passed has started again, whatever share it was read at (`resetPassed`). That holds for a reading kept from before (`AsOf`) and for a fresh one: Claude Code's `/usage` gives a reset to the minute and can lag it, so a run just after a reset can still say 100% with that reset. `claudeWindows` hands such a window back empty on every path, and `usedPast`, `usedUp`, `BackAt` and `capReached` leave it out when they judge an account spent, for Codex, Claude Code and `magpie quota wait` alike. A card can still show a kept reading as it was read (`reported`, for a Claude card while `/usage` is unavailable); that changes what it shows, never which account is used. A reset `/usage` gives as a time alone ("resets 3pm") can be read as its next one, a day on (`claudeResetTime`), and is then not seen as passed here.
- A restart to update can run two magpies for up to the old one's drain
  ([GUI shell](gui-shell.md#a-restart-to-update-hands-the-gateway-over)), each
  able to refresh a sign-in. A refresh that rotates its refresh token holds
  a file lock beside `logins.json`, so the second waits and takes the
  first's tokens instead of spending the used one: Codex's `auth.json`
  (`codexMu`, `.codex.lock`) and the ChatGPT API's sign-in (`siwcRefreshing`,
  `.siwc.lock`) since this change; Claude's saved tokens (`savedTokenMu`),
  MCP servers' (`mcpauth`'s renew lock) and plugins' were already held so.
  Google's, Vertex AI's and Copilot's refresh tokens don't rotate. Claude
  Code run in its own folder (`claudeDirRun`) is held in this process only;
  the bridge's turns hold the restart back, so the two don't overlap there.
  `TestCodexRefreshWaitsForAnotherMagpie`,
  `TestChatGPTAPIRefreshWaitsForAnotherMagpie`.
- A switch of Claude Code's sign-in (`switchSavedLogin`) and a sign-in
  that may write it (`addLogin`) take Claude Code's own refresh locks
  first ([claude_lock.go](../../internal/provider/claude_lock.go)), as
  Claude Code 2.1.316 takes them: the directory
  `<config dir>/.oauth_refresh.lock`, then `<realpath(config dir)>.lock`
  (`~/.claude.lock`), each made with mkdir, touched while held and taken
  over once untouched for 60s. Rewriting `~/.claude.json`'s
  `oauthAccount` (`putClaudeLogin`) takes `<that file>.lock` (10s stale)
  after them, the order Claude Code saves it in. A switch read during a
  refresh kept the outgoing account with the refresh token that refresh
  spent, so it was signed out of magpie on its next use (#4532). A lock
  held past 20s fails the switch with nothing written (`errClaudeLocked`).
  magpie writes no `.oauth_refresh.lock.owner`, so Claude Code waits out a
  lock magpie left only by its stale time. Other `~/.claude.json` writers
  (the Library's MCP servers) don't take the lock yet (#4747).
  `TestClaudeSwitchWaitsForClaudeCodesRefresh`,
